# 실시간 모니터링 (AI 사용량 + 자원 사용량) 구현 가이드라인

작성: 2026-11-09 · 구현 전 (이 문서만 있고 코드는 바꾸지 않았다) · 버전은 배포할 때 정한다 (번호를 말하지 않으면 1.4.2)

AI 사용량 상시 표시에 CPU·GPU·MEM·디스크 사용량을 더하는 기능의 구현 방향, 일어날 수 있는 충돌·오류와 해결, 작동 방식, 구현 순서를 정리한다.
수치는 이 Mac(MacBook, Apple Silicon 14코어, 메모리 26GB, SSD 995GB, macOS 27.3)에서 직접 잰 값이다. 코드 위치는 작성 시점(1.4.1)의 파일과 줄이다.

---

## 0. 결론

1. **종류를 늘리되 기존 `.aiUsage`는 건드리지 않는다.** 자원 사용량은 새 종류 `.resource`, 둘을 한 활동으로 합친 것은 `.monitor`다. 노치 양옆의 칸 두 개(왼쪽·오른쪽)가 각각 무엇을 보일지만 정하면 AI 전용·자원 전용·둘 다가 모두 같은 구조로 표현된다 (§3.2).
2. **자원은 "필요한 것만, 보이는 동안만" 읽는다.** 노치에 보이는 칸(0~2개)과 확장 페이지(4개)를 합쳐 *수요*를 계산하고, 수요가 있는 동안만 타이머 하나가 돈다. 보이는 칸이 없으면 타이머도 없다 (§4.2).
3. **읽는 비용은 작다. 단, 읽는 방법에 따라 3000배 차이가 난다.** CPU 34µs, MEM 5µs, 디스크 `statfs` 1.8µs, GPU 920µs. 디스크를 `URL.resourceValues`로 읽으면 5.1ms라 쓰지 않는다 (§2).
4. **진짜 비용은 읽기가 아니라 화면 다시 그리기다.** 값을 활동(`NotchActivity`) 안에 넣으면 매초 `ActivityCenter`가 바뀌어 노치 전체가 다시 그려진다. 값은 별도 저장소에 두고 작은 뷰 하나만 갱신한다 (§4.3).
5. **메모리 누적은 구조로 막는다.** 기록은 쌓지 않고(최신 값만), 멈추면 전부 버리고, 이 앱의 할당기가 메모리를 돌려주지 않는 성질(`MemoryGuard` 주석) 때문에 **장시간 시험을 합격 조건**으로 둔다 (§4.6, §7).
6. **요구에서 해석이 갈리는 곳이 4군데 있다.** 권장안과 함께 §9에 모았다. 특히 "디스플레이별 따로 표시"와 "둘 다로 통합"의 관계(§3.3)는 구조를 좌우하므로 먼저 확인해야 한다.

## 2. 측정한 사실

`scripts/resource-bench.swift`로 잰 값이다 (평균, 200~500회).

### 2.1 읽는 비용

| 지표 | 방법 | 1회 비용 | 비고 |
|---|---|---|---|
| CPU | `host_processor_info(PROCESSOR_CPU_LOAD_INFO)` 두 번의 차이 | **34µs** | 14코어. 호출마다 mach 메모리가 할당되어 **`vm_deallocate`를 꼭 해야 한다** |
| MEM | `host_statistics64(HOST_VM_INFO64)` | **5.4µs** | 아래 정의 참고 |
| DISK | `statfs("/System/Volumes/Data")` | **1.8µs** | 시작 볼륨의 데이터 영역 |
| DISK (비교) | `URL.resourceValues(volumeAvailableCapacity…)` | 5,110µs | **2,800배 느리다. 쓰지 않는다** |
| GPU | `IOAccelerator`의 `PerformanceStatistics` | **920µs** | 가장 비싸다. 레지스트리 속성 사전을 통째로 만든다 |

- 네 개를 모두 매초 읽어도 약 1ms/초(CPU 0.1%). 칸에 보이는 1~2개(예: CPU+MEM)는 40µs/초로 무시할 수 있다. **GPU를 고른 때만 비용이 눈에 띈다.**
- GPU 키 `Device Utilization %`(그 밖에 `Renderer Utilization %`, `Tiler Utilization %`)가 이 Mac에 있다. 비공개 레지스트리 키라 macOS 업데이트로 바뀔 수 있다 → §6.

### 2.2 지표 정의 (노치에 쓸 값)

| 지표 | 정의 | 이 Mac의 값 |
|---|---|---|
| CPU | 전체 코어의 (user+system+nice) 틱 ÷ 전체 틱. 샘플 사이의 차이 | 코어 14 |
| MEM | **활동 상태 보기의 '사용한 메모리'**: (internal − purgeable + wired + compressed) 페이지 ÷ 전체 메모리 | 15.0GB / 25.8GB = 58% |
| DISK | 데이터 볼륨 사용률 = 1 − 사용 가능 ÷ 전체 (용량 기준, 읽기·쓰기 속도 아님) | 449.6GB 남음 / 995GB = 55% 사용 |
| GPU | `Device Utilization %` | 대기 중 0 |

- MEM은 `top`의 `PhysMem 23G used`와 다르다. `top`은 파일 캐시를 사용 중으로 센다(`active+wired+compressed`로 계산한 값도 14.5GB로 달랐다). 활동 상태 보기와 맞는 정의는 위 표의 것이다. **구현 때 활동 상태 보기와 직접 대조한다 (R1).**
- Finder의 "사용 가능"은 지울 수 있는 공간(459.4GB)을 포함해 `statfs`(449.6GB)와 1%p 안팎으로 다르다. 노치에는 `statfs`를 쓰고 확장 페이지에 "사용 가능 N GB"를 보이면 Finder와 약간 다를 수 있다.

### 2.3 아직 재지 못한 것 (R1에서 잰다)

- 매초 값이 바뀔 때 SwiftUI가 다시 그리는 CPU 비용 (이게 핵심이다 — §4.3)
- 1시간 연속 측정 때의 메모리 증가
- GPU 속성을 한 키만 읽는 방법(`IORegistryEntryCreateCFProperty`)이 920µs보다 싼지
- 화면이 꺼진 동안 GPU·CPU 읽기가 의미 있는지

## 3. 요구 정리와 해석

### 3.1 용어

| 한국어 | English | 비고 |
|---|---|---|
| 실시간 모니터링 | Live Monitoring | 설정 페이지 이름. 지금의 "AI 사용량" 페이지를 바꾼다 (사이드바·카드·README·이름표) |
| AI 사용량 | AI Usage | 홈 기능(홈의 페이지) 이름은 그대로 |
| 자원 사용량 | Resource Usage | 새 용어 |
| 표시할 항목 | Show | AI 사용량 / 자원 사용량 / 둘 다 |
| 칸 (왼쪽·오른쪽) | Slot (Left, Right) | 노치 양옆의 값 하나 |
| 통합 | Combined | AI 및 자원 사용량 |

저장 키와 `SettingsPage.aiUsage`의 rawValue, `ActivityKind.aiUsage`는 **바꾸지 않는다** (저장된 설정·순위·디스플레이 선택이 이 이름으로 저장되어 있다). 화면에 보이는 이름만 바꾼다. `docs/ARCHITECTURE.md`의 용어표에 위 용어를 추가한다.

### 3.2 칸 규칙

노치 양옆의 값 두 칸을 `(왼쪽, 오른쪽)`으로 본다. 고를 수 있는 항목은 `aiPrimary`(AI 5시간, 한도가 하나면 전체), `aiSecondary`(AI 주간), `cpu`, `gpu`, `mem`, `disk` 여섯 가지다.

| 표시할 항목 | 왼쪽 | 오른쪽 | 고르는 방법 |
|---|---|---|---|
| AI 사용량 | 5시간 | 주간 | 고정. 서비스만 고른다 (지금과 같음) |
| 자원 사용량 | CPU·GPU·MEM·디스크 중 하나 | 나머지 중 하나 | 한쪽을 고르면 반대쪽 목록에서 그 항목이 비활성 |
| 둘 다 | 여섯 항목 중 하나 | 여섯 항목 중 하나 | 같은 항목을 양쪽에 둘 수 없다 (같은 방식으로 비활성) |

- 자원 전용과 둘 다의 선택은 **모드마다 따로 기억한다** (`resourceLeft/Right`, `bothLeft/Right`). 모드를 오가도 고른 것이 사라지지 않는다. 기본값은 자원 전용 CPU·MEM, 둘 다 AI 5시간·CPU.
- 모드를 바꿀 때 저장값이 그 모드에서 불가능하면(예: 둘 다에 있던 `aiPrimary`가 자원 전용으로) 기본값으로 푼다. 이 계산은 화면과 분리한 순수 함수 `MonitorLayout`에 둔다 (§8 R2).
- AI 항목을 골랐는데 연결된 서비스가 없으면 칸은 `–`를 보이고 설정에 "로그인 필요"를 표시한다. 선택 자체를 막지는 않는다.
- **AI 한도가 하나뿐인 서비스**(예: ChatGPT 무료 30일)에서 *전체 사용량*을 보이는 방법은 §3.5.

### 3.3 디스플레이별 표시와 통합 — 해석과 권장안

요구에서 구조에 가장 큰 영향을 주는 부분이다. 문장 그대로는 둘로 읽힌다.

- 문장 A: 자원 사용량이 켜진 상태에서 **디스플레이마다 AI·자원을 따로** 둘 수 있다 (예: 메인 = 자원, 보조 = AI).
- 문장 B: "둘 다"를 고르면 **자동으로 통합**된다 (두 디스플레이 모두 "AI 및 자원 사용량").

"표시할 항목"의 세 값만으로는 "메인 = 자원, 보조 = AI"가 동시에 존재할 수 없다(단일 모드에서는 한 종류만 돌기 때문). 그래서 **권장하는 해석**은 이렇다.

1. **표시할 항목(전역)** 은 *기본 내용*이다: "모든 상시 표시"·"주 디스플레이와 같게"로 둔 디스플레이에 무엇이 뜨는지를 정한다.
2. **디스플레이별 상시 표시**(설정 → 디스플레이)는 지금처럼 디스플레이마다 `AI 사용량`·`자원 사용량`을 직접 고를 수 있다. 직접 고른 디스플레이는 전역 값과 상관없이 그것을 보인다.
3. 전역이 **둘 다**이면 위 선택과 상관없이 모든 디스플레이가 통합(`.monitor`)이 된다. **저장값은 건드리지 않고** 읽을 때만 바꿔 해석한다. 그래서 다시 단일 모드로 돌아가면 직접 골랐던 값이 되살아난다.

| 단계 | 전역 | 메인(저장값) | 보조(저장값) | 화면에 보이는 것 | 도는 것 |
|---|---|---|---|---|---|
| ① | AI 사용량 | 자원 사용량 | AI 사용량 | 메인 자원, 보조 AI | AI 새로고침 + 자원 측정(메인이 보이는 동안) |
| ② | **둘 다**로 변경 | (그대로) | (그대로) | 두 디스플레이 모두 AI 및 자원 사용량 | 통합 활동 하나 |
| ③ | AI 사용량으로 복귀 | 자원 사용량 | AI 사용량 | ①과 같음 | ①과 같음 |

- 설정 → 디스플레이의 목록은 전역이 둘 다일 때 "AI 사용량"·"자원 사용량" 대신 **"AI 및 자원 사용량"** 한 줄을 보인다 (`kind:monitor`). 이때 직접 바꾸면 `kind:monitor`가 저장된다. 단일 모드로 돌아가면 `kind:monitor`는 그 모드의 종류로 푼다 (AI 사용량 모드 → `aiUsage`, 자원 사용량 모드 → `resource`).
- "모든 상시 표시"(`all`)는 **전역 모드에 포함된 모니터 종류만** 포함한다. 보조가 자원을 직접 골라 자원 활동이 돌고 있어도, 메인의 "모든 상시 표시"에 자원이 끼어들지 않는다.
- **활동이 존재하는 조건**: 어떤 종류의 활동은 *켜진 디스플레이 중 하나라도 실제 표시 내용이 그 종류일 때만* 게시한다. 이 계산(`neededMonitorKinds`)도 순수 함수로 두고 `--display-probe`에 조합 시험을 더한다.

다른 해석(전역 값이 곧 디스플레이를 덮어쓴다 등)이면 이 절의 규칙 표만 바뀐다. 활동 종류·샘플러·수요 계산은 그대로다. 그래서 **§9의 결정 1을 먼저 확인**하고 R4 전에 확정하면 된다.

### 3.4 길게 눌렀을 때 확장 컨텐츠

설정 항목 `monitorExpand`(꾹 눌렀을 때 보일 내용): **AI 사용량 / 자원 사용량 / 둘 다**. 기본은 표시할 항목을 따른다.

- AI 사용량: 지금과 같다 (AI만 상시일 때 홈의 AI 사용량 페이지, 그 밖에는 팝업).
- 자원 사용량: 팝업 하나 (2×2 격자 네 지표).
- 둘 다: 팝업 안에 페이지 두 개(AI, 자원)를 점으로 넘긴다. `persistentPages`가 `.monitor`를 두 페이지로 펼쳐 기존의 점·두 손가락 넘기기를 그대로 쓴다 (§4.5).
- 통합 활동을 눌렀을 때 시작 페이지는 *누른 칸 쪽*이 아니라 설정에 따른다 (칸 기준은 사용자가 예측하기 어렵다).

### 3.5 AI "전체 사용량"(한도가 하나인 서비스)

요구: 전체 사용량을 보이는 경우(한 가지만) 왼쪽에 서비스 기호(GPT·Claude·Gemini)를 표시한다. 지금은 왼쪽에 사용률, 오른쪽에 초기화까지 남은 시간이다.

권장: **왼쪽 = 서비스 기호, 오른쪽 = 사용률**. 초기화까지 남은 시간은 노치에서 빠지고 확장 페이지·툴팁에는 그대로 있다. (§9의 결정 2)

서비스 기호는 새로 만든다. 저장소에 로고 이미지가 없고 앱에 상표 이미지를 넣고 싶지 않으므로, `BluetoothGlyph`처럼 코드로 그리는 단순한 도형을 서비스 색으로 칠한다 (Claude: 방사형 별, Gemini: 네 꼭지 별, ChatGPT: 둥근 육각 고리). **원본 로고가 아니다.** 마음에 안 들면 서비스 색 원 안에 `GPT`·`CL`·`GM` 두 글자가 대안이다. (§9의 결정 3)

## 4. 구조

### 4.1 종류와 활동

```
UsageStore ──(AI 값, 분 단위)──┐
                                ├─ MonitorCoordinator ── 활동 게시: .aiUsage / .resource / .monitor
ResourceSampler ──(자원 값)────┘
                    ▲ 수요(어떤 지표가 보이는가)
                    └─ NotchHub (디스플레이별 표시 상태에서 집계)
```

| 종류 | 언제 게시 | 칸 내용 |
|---|---|---|
| `.aiUsage` (기존) | AI가 필요할 때 | 5시간 / 주간 (또는 §3.5) |
| `.resource` (새) | 자원이 필요하고 통합이 아닐 때 | 자원 전용 칸 두 개 |
| `.monitor` (새) | 전역이 둘 다 | 둘 다 칸 두 개 |

- 새 종류를 둘 다 두는 이유: 디스플레이마다 다른 내용을 고르려면 *서로 다른 활동*이 동시에 있어야 하고(§3.3), 통합 활동은 칸마다 AI/자원이 섞이기 때문이다. `.aiUsage`에 통합까지 얹으면 디스플레이 규칙과 이름이 혼란스러워진다.
- 순위: 사용자가 정하는 우선순위 목록(설정 → 우선순위)에는 `자원 사용량` 한 줄을 `AI 사용량` 바로 아래에 기본으로 넣는다 (`defaultPersistentOrder`에 `resource`, 기존 사용자는 "새 항목은 기본 순서대로 뒤에 붙인다" 규칙으로 자동). `.monitor`는 자기 줄이 없고 **`aiUsage`와 `resource` 순위 중 높은 쪽**을 쓴다 (`orderedPersistent`의 `rank`에 한 줄).
- `.monitor`·`.resource`도 `pagedKinds`에 넣어 길게 누르면 확장 화면이 열리게 한다.

### 4.2 ResourceSampler

새 파일 `Monitors/ResourceSampler.swift`. 지금 `Monitors/`의 다른 감시자와 같은 위치·이름 규칙이다.

```swift
enum ResourceMetric: String { case cpu, gpu, mem, disk }

final class ResourceSampler {          // 앱에 하나, 처음 수요가 생길 때 만든다 (lazy)
    private(set) var readings = ResourceReadings()   // §4.3
    func setDemand(_ owner: DemandOwner, _ metrics: Set<ResourceMetric>)   // 수요 등록·해제
    // 내부: 수요 합집합 = 읽을 지표, 합집합이 비면 타이머 해제
}
```

- **수요는 소유자별로 등록한다**: `compact(디스플레이)`와 `expanded(디스플레이)`. 합집합이 읽을 지표다. 디스플레이 A가 CPU·GPU, B가 MEM을 보이면 세 지표를 *한 번씩만* 읽는다.
- **타이머는 하나**: `DispatchSourceTimer`, 간격은 설정(1·2·5·10초), 허용 오차(leeway)는 간격의 10~20%로 다른 깨어남과 묶이게 한다. 수요가 비면 `cancel()`하고 참조를 버린다. 간격이 바뀌면 다시 만든다 (설정 변경은 300ms 모아서 한 번).
- **지표별 읽기**: 수요에 없는 지표는 호출하지 않는다 (GPU는 선택하지 않으면 920µs를 아예 쓰지 않는다). 디스크는 값이 느리게 변하므로 직전 읽기에서 30초가 안 지났으면 이전 값을 쓴다 (비용이 아니라 의미 없는 갱신을 줄이는 이유).
- **CPU 첫 값**: CPU는 두 샘플의 차이라 켜진 직후 값이 없다. 수요가 생기면 즉시 한 번 읽고 **0.25초 뒤에 한 번 더** 읽어 첫 값을 만든다 (그 전에는 `–`). 길게 눌러 확장했을 때 CPU가 새로 필요해져도 같은 방식이다. 이미 CPU를 읽고 있었다면 바로 값이 있다. 틱 차이는 `UInt32` 감소 연산(`&-`)으로 한 바퀴 돌아도 맞다.
- **일시 정지 뒤 재개**: 직전 틱과 시간 차가 간격의 3배를 넘으면(잠자기 등) 그 차이는 버리고 워밍업을 다시 한다.
- **한 틱은 `autoreleasepool`로 감싼다.** `host_processor_info`의 mach 버퍼는 `vm_deallocate`하고, IORegistry 사전은 풀 안에서 해제한다. 누수 도구(`leaks`)는 mach 가상 메모리를 보지 않으므로 **이 해제는 코드로 직접 보장하고 soak 시험으로 확인한다.**

### 4.3 값 저장소와 라이브 뷰 (매초 노치 전체를 다시 그리지 않기)

지금 구조에서는 `center.setPersistent(activity)`가 바뀔 때마다 `ActivityCenter`가 `objectWillChange`를 보내고, `DisplayNotchState`가 이를 그대로 전달해 노치 전체가 다시 그려진다 (`DisplayNotchState.swift:132`, `ActivityCenter.setPersistent`의 "내용이 같으면 다시 게시하지 않는다"). 매초 퍼센트가 바뀌는 값을 이 길로 보내면 매초 노치 전체를 다시 그린다.

- 새 `ActivityValue.metric(MonitorMetric, ring: Bool)`를 둔다. **활동은 "이 칸에 CPU를 그려라"라는 내용만 갖고 값은 갖지 않는다.** 그래서 틱마다 활동이 바뀌지 않는다.
- 칸을 그리는 작은 뷰 `LiveMetricView`가 `ResourceReadings`(별도 `ObservableObject`)를 관찰한다. 값이 바뀌면 이 뷰 하나만 다시 그려진다.
- 같은 값이면 게시하지 않는다: **정수 퍼센트로 반올림해 같으면 갱신을 건너뛴다.** 대부분의 틱에서 GPU·디스크·MEM은 값이 같으므로 거의 그려지지 않는다.
- 자리가 흔들리지 않게 숫자는 `monospacedDigit`, 폭은 "100%"가 들어가는 고정 폭으로 한다 (칸 폭은 지금과 같은 `compactWing`).
- 색은 `UsageGlyph.color`를 그대로 쓴다 (70%↑ 주황, 90%↑ 빨강). 표시 형태(텍스트/원형)는 `aiUsageStyle`을 AI와 자원이 함께 쓴다.
- 접근성: 값이 계속 바뀌는 뷰는 `accessibilityAddTraits(.updatesFrequently)`로 매번 읽어 주지 않게 한다.
- **이 설계가 효과가 있는지는 R1의 프로토타입 측정으로 확인한다.** 효과가 없으면(예: 뷰 한 개 갱신도 전체 갱신을 부른다) 이 절을 고친다.

### 4.4 DisplayRules 변경

`Notch/DisplayRules.swift`는 순수 계산이라 시험이 쉽다. 여기에 아래를 더한다.

| 함수 | 하는 일 |
|---|---|
| `effectiveChoice(_:global:)` | §3.3의 읽기 시 해석: 전역이 둘 다이면 `kind:aiUsage`·`kind:resource`·`kind:monitor` → `kind:monitor`. 단일 모드에서 `kind:monitor` → 그 모드의 종류 |
| `persistentKinds(...)` 수정 | `all`은 전역 모드에 포함된 모니터 종류만 포함. `kind:resource` 선택이 비활성이면(자원 활동 없음) 지금의 "주 디스플레이 대체" 규칙을 그대로 따른다 |
| `neededMonitorKinds(contexts:global:)` | 켜진 디스플레이들의 실제 표시 내용에서 게시해야 할 모니터 종류 집합 |

`DisplayProbe`에 모드 3종 × 디스플레이 선택 조합(직접 선택 포함) × 대체 켬/끔을 돌리는 검사를 더해, **통합 전후 저장값이 바뀌지 않는다**와 **`all`에 남의 종류가 끼지 않는다**를 확인한다.

### 4.5 확장 페이지

- `ResourcePage`(새): 지표 네 개를 2×2 격자로. 칸마다 이름·막대(`BarGauge`)·값. MEM은 "사용 N GB / 전체 M GB", 디스크는 "사용 가능 N GB"를 작은 글씨로. 크기는 `usageSize`(300×124)에 들어가게 한다. 안 맞으면 `popupSize`에 자원 전용 크기를 더한다.
- 확장 중에만 네 지표를 읽는다 (`expanded(디스플레이)` 수요 = 네 개). 확장이 끝나면 **0.5초 뒤** 수요를 거둔다 (다시 열 때 깜빡임과 CPU 워밍업을 피한다).
- "둘 다" 확장: `persistentPages`(`DisplayNotchState.swift:504`)가 `.monitor`를 `[.aiUsage, .resource]`(설정에 따라 한쪽만)로 펼친다. 점·넘기기(`showsPersistentDots`, `selectPersistentPage`)는 그대로 쓴다.
- `AppDelegate+NotchActions.swift`의 `pagedKinds`와 `collapseIfActivityGone`의 목록에 새 종류를 더한다 (활동이 사라지면 확장도 닫는다).
- 새로고침 단추: 자원 페이지에는 두지 않는다 (실시간이라 의미가 없다). AI 페이지는 지금대로.

### 4.6 누적을 막는 장치

요구: "모니터링 내용이 계속 누적되어 메모리가 늘지 않게, 주기적으로 캐시를 비우는 장치".

1. **구조적 상한**: 저장하는 것은 *지표별 최신 값 하나*와 CPU 이전 틱 배열(14×4개의 `UInt32`)뿐이다. 과거 기록(그래프)은 첫 버전에 넣지 않는다. 기록이 없으면 누적될 것도 없다. (그래프가 필요해지면 길이 60 고정 링 버퍼로, 확장 중에만 쌓고 닫으면 버린다.)
2. **멈추면 전부 버린다**: 수요가 0이 되면 `reset()`으로 이전 틱·최신 값·시각을 지운다. `MemoryTrim.soon()`도 부르지만 **이 장치에 기대지 않는다**: 소스 주석대로 xzone 할당기를 쓰는 최신 macOS에서는 돌려주는 양이 0이다.
3. **메모리 지킴이 연결**: `MemoryGuard.releaseCaches`(`AppDelegate.swift:199`)에서 `ResourceSampler.compact()`를 부른다 (읽기 버퍼·포맷 캐시 정리 — 쌓인 것이 있다면). 지킴이가 기준 초과로 재시작하려 할 때도 측정 중이라는 이유로 막지 않는다(`isIdleForRelaunch`의 `busyKinds`에 넣지 않음).
4. **연속 측정 중 주기 정리**: 연속 10분마다 `compact()`를 한 번 부른다. 이 값은 §7의 soak 결과로 조정한다. **soak에서 증가가 없다면 이 주기 정리는 넣지 않는다** (필요 없는 코드를 두지 않는다).
5. **왜 이게 필요한가**: 이 앱은 최신 macOS의 할당기가 해제한 메모리를 운영체제에 돌려주지 않는 성질 때문에 큰 작업 뒤 사용량이 그대로 남고, "캐시를 비운다"로 되돌릴 수 있는 양이 거의 없다(`MemoryGuard`·`MemoryTrim` 주석). 그래서 **1~4의 구조(애초에 쌓지 않기)가 본체이고**, 매초 문자열·뷰 값을 만드는 작업이 증가를 일으키는지는 **장시간 시험이 판정한다.** 증가가 확인되면 마지막 수단은 기존 `MemoryGuard`의 조용한 재시작이다. 사용자가 정한 70MB 기준이 그대로 안전망이 된다.

### 4.7 측정을 멈추는 조건

AI는 "우선순위가 더 높은 항목에 가려지면 새로고침을 쉬고, 두 손가락으로 잠시 숨긴 동안은 계속한다"(`updateCoverage`). 자원은 *보이지 않으면 읽을 이유가 없고*, 다시 보일 때 즉시 읽을 수 있으므로 더 적극적으로 쉰다.

| 조건 | 자원 측정 |
|---|---|
| 어느 디스플레이에도 자원 칸이 보이지 않음 (더 높은 상시 항목이 가림, 항목 선택에서 제외, 노치 없음) | 정지 |
| 두 손가락으로 상시 표시를 숨김 (`persistentHidden`) | **정지** (AI와 다르다) |
| Mission Control로 숨김 / 화면 잠금 / 패널 숨김 | 정지 |
| 화면 꺼짐, 시스템 잠자기 | 정지 (`NSWorkspace.screensDidSleep`, `willSleep`) → 깨어나면 워밍업 |
| 일회성 알림이 잠깐 가림 (수 초) | 계속 (끊고 이으면 오히려 비싸다) |
| 저전력 모드 | 간격을 2배로 (선택, §9 결정 6) |

신호의 출처는 `NotchHub.setMissionControlActive`·`setMainPanelsHidden`, `ActivityCenter.persistentHidden`·`hiddenFromScreen`, 각 디스플레이의 `displayed`다. 수요 집계는 `NotchHub`가 맡고 300ms 모아서 `ResourceSampler.setDemand`에 넘긴다. 이 집계도 순수 함수로 분리해 `--monitor-probe`로 시험한다 (§8 R1).

## 5. 설정 화면과 저장 키

### 5.1 페이지 구성 ("실시간 모니터링")

기능 페이지 규칙(표시 → 상시 표시 → 표시 방식 → 세부 설정 → 미리보기)을 따른다.

| 구역 | 항목 |
|---|---|
| 표시 | 홈에 AI 사용량 페이지 표시 (지금과 같음) |
| 상시 표시 | **노치에 상시 표시** 스위치(전체 켜기·끄기) · **표시할 항목** (AI 사용량 / 자원 사용량 / 둘 다, 버튼형) · 칸 선택: 자원 전용·둘 다일 때 **왼쪽**·**오른쪽** 메뉴(고른 항목은 반대편에서 비활성) · AI 서비스 선택(AI 칸이 있을 때) |
| 표시 방식 | 표시 형태(텍스트/원형)  ·  꾹 눌렀을 때 보일 내용 |
| 세부 설정 | AI 새로고침 빈도(분, 지금과 같음) · **자원 새로고침 빈도**(1·2·5·10초, 자원 칸이 있을 때) · 서비스 로그인 목록 |
| 미리보기 | 상시 표시(AI) · 자원(가짜 값) · 통합(가짜 값) |

- 칸 메뉴는 `MenuChoice`로 한다. 항목이 여섯이라 버튼형이 아니라 메뉴가 맞다 (`docs/ARCHITECTURE.md`의 선택 규칙).
- 자원 칸·새로고침 빈도는 표시할 항목에 자원이 없으면 `SettingsSection(disabled:)`로 흐리게 한다.
- 글씨 안내: GPU는 이 Mac에서 읽을 수 없으면 메뉴에서 비활성으로 두고 이유를 한 줄로 적는다 (§6).
- 개인정보 안내: 자원 사용량은 이 Mac 안에서만 읽고 어디로도 보내지 않는다고 한 줄 적는다 (기존 AI 사용량은 웹에 로그인해 읽는다는 안내가 있어서 구분이 필요하다).
- 사이드바 이름은 "실시간 모니터링 / Live Monitoring". 아이콘은 지금의 `gauge.medium`을 그대로 쓴다 (둘 다에 어울린다).

### 5.2 저장 키

기존 키는 **하나도 바꾸지 않는다.**

| 키 | 값 | 기본 | 비고 |
|---|---|---|---|
| `aiUsagePinned` (기존) | Bool | false | **전체 상시 표시 스위치로 재해석.** 켜 둔 사용자는 그대로 AI 사용량 상시 표시가 유지된다 |
| `aiUsageStyle`, `aiUsageService`, `aiRefreshMinutes`, `aiConnected` (기존) | | | 그대로. 표시 형태는 자원도 같이 쓴다 |
| `monitorContent` | `ai` / `resource` / `both` | `ai` | 기존 사용자는 지금과 같게 보인다 |
| `monitorExpand` | `follow` / `ai` / `resource` / `both` | `follow` | 표시할 항목을 따르는 것이 기본 |
| `resourceLeft`, `resourceRight` | `cpu`/`gpu`/`mem`/`disk` | `cpu`, `mem` | 자원 전용 |
| `bothLeft`, `bothRight` | 여섯 항목 | `aiPrimary`, `cpu` | 둘 다 |
| `resourceRefreshSeconds` | 1·2·5·10 | 2 | 읽을 때 이 값 외에는 2로 |
| `persistentOrder` | 기존 + `resource` | | 새 항목은 기본 순서대로 자동 추가 |
| `displayContent` (기존) | 값에 `kind:resource`, `kind:monitor` 추가 | | 저장 형식은 그대로 |

모두 `@Setting`으로 선언한다 (`ARCHITECTURE.md`). `--settings-probe`에 "기존 값 그대로 읽힘"(`aiUsagePinned` 마이그레이션), "모르는 값은 기본값"을 더한다.

## 6. 일어날 수 있는 충돌·오류와 해결

| # | 상황 | 문제 | 해결 |
|---|---|---|---|
| 1 | 홈의 "AI 사용량" 기능을 끔 | `UsageStore.connected`가 비어 상시 표시가 사라진다. 자원까지 사라지면 이상하다 | 홈 기능 스위치는 **AI 쪽만** 막는다. 자원은 `aiUsagePinned`(전체 스위치)와 표시할 항목만 따른다. 홈 기능 안내 문구도 "AI 사용량"으로 한정해 적는다 |
| 2 | 매초 값이 바뀌어 `ActivityCenter`가 계속 갱신 | 노치 전체가 매초 다시 그려져 CPU가 오른다 | §4.3: 값은 별도 저장소, 활동은 불변. R1에서 측정해 확인 |
| 3 | `host_processor_info`의 mach 버퍼를 해제하지 않음 | 누수 도구에 안 잡히는 가상 메모리 누수 | `vm_deallocate` + soak(1시간)에서 `footprint`가 평탄한지 확인 |
| 4 | CPU 첫 값이 0% | 확장하자마자 `0%`가 보이는 거짓 값 | 0.25초 워밍업, 그 전에는 `–` |
| 5 | 잠자기·화면 꺼짐 뒤 첫 CPU 값 | 긴 시간 평균이 한 번에 나와 튐 | 시간 차가 간격의 3배를 넘으면 버리고 워밍업 |
| 6 | GPU 키가 없음 (macOS 업데이트·가상 머신) | 값이 `–`로 굳거나 읽기를 계속 시도 | 연속 3번 실패하면 읽기를 멈추고 설정에서 GPU를 비활성으로 표시. 칸에 이미 GPU가 선택돼 있으면 `–`와 설명 |
| 7 | 칸에 GPU를 고른 채 1초 간격 | 920µs/초 (CPU 0.1%) | 허용. 설정에 비용 안내는 넣지 않는다 (작다). R1에서 한 키만 읽는 방법이 더 싼지 측정 |

| 9 | 메인=자원, 보조=AI 상태에서 "모든 상시 표시"(`all`) 디스플레이 | 자원이 `all`에 끼어듦 | §3.3: `all`은 전역 모드에 포함된 종류만 |

| 11 | "둘 다"에서 두 칸이 같은 항목 | 의미 없음 | 메뉴에서 같은 항목을 반대편에서 비활성. 저장값이 이미 같으면(이전 값) `MonitorLayout`이 풀어 준다 |
| 12 | AI 항목을 골랐는데 로그인한 서비스가 없음 | 빈 칸 | `–` 표시, 설정에 "로그인 필요" |
| 13 | 한도가 하나뿐인 서비스의 `aiSecondary` | 지금은 오른쪽에 초기화 시간 | 둘 다에서 `aiSecondary`가 한도 하나인 서비스면 `–`가 아니라 "초기화까지 남은 시간"(지금 방식)을 보인다. AI 전용은 §3.5 |
| 14 | 우선순위에서 자원이 미디어 아래 | 음악이 나오면 자원이 가려져 안 보임 (측정도 쉼) | 의도된 동작이다. 설정 우선순위 안내에 한 줄. 기본 순서에서 `resource`는 `aiUsage` 바로 아래 |
| 15 | 미리보기가 샘플러를 켬 | 미리보기가 끝났는데 타이머가 남음 | 자원 미리보기는 **가짜 값만 쓰고 샘플러를 켜지 않는다** (`FeaturePreview`는 모든 흔적을 거둔다는 원칙) |
| 16 | 설정 창(도우미)에서 값을 바꿈 | 본 앱에 반영 지연 | 기존 `settingsChanged` 분산 알림 경로. `resourceRefreshSeconds` 등을 구독해 300ms 모아서 타이머 재생성 |
| 17 | 간격 1초 + 알림이 자주 뜨는 환경 | 타이머가 알림 표시와 겹쳐 깨어남 증가 | leeway로 묶고, 대기 깨어남이 초당 +1을 넘지 않는지 §7에서 확인 |

| 23 | 색 임계값 | CPU 70%는 평소에도 자주 넘음 | AI와 같은 임계값을 쓰되, 실사용에서 거슬리면 CPU는 90%/98%로 따로 둔다 (R3에서 확인) |

## 7. 자원 예산과 시험

### 7.1 합격 기준 (제안, R1 측정 뒤 확정)

| 항목 | 기준 |
|---|---|
| 기능을 쓰지 않을 때(기본: AI 사용량 모드) | **추가 비용 0**: 샘플러 생성 안 됨, 타이머 0개, 실행 직후 메모리·대기 CPU가 1.4.1과 같음 (17.2MB / 0.07~0.10%) |
| 칸 1~2개(CPU·MEM), 1초 | 대기 CPU ≤ 0.5%, 메모리 +1MB 이내, 대기 깨어남 +1/초 이내 |
| 확장 페이지(4지표) 열림, 1초 | CPU ≤ 1.5% (열려 있는 동안) |
| 확장을 닫은 뒤 | 1초 안에 쓰지 않는 지표 읽기 중단, 수요가 0이면 타이머 0개 |
| **연속 1시간 측정(1초, CPU+GPU+MEM)** | 시작 5분 이후 `footprint` 증가 ≤ 2MB, `leaks` 0건 |
| 연결을 끊고 다시 열기 50회 | 메모리 증가 없음 (수요 등록·해제 누수 확인) |
| 컴파일 경고 | 프로젝트 코드 0건 |

### 7.2 시험 항목

- **`--monitor-probe`** (새, 개발 빌드): 수요 집계(디스플레이 2개 × 칸·확장 조합 × 숨김 조건), `MonitorLayout`(모드 전환·같은 항목·모르는 값), `neededMonitorKinds`, 통합 해석의 가역성, `.monitor` 순위 규칙. 실패 0건.
- **`--display-probe` 확장**: §4.4.
- **`--settings-probe` 확장**: §5.2.
- **`notchctl monitorstate`**(새): 읽는 지표, 간격, 타이머 유무, 틱 수, 사이 `footprint`를 `$TMPDIR/dmn-monitor.txt`에 기록. 시험 스크립트가 "타이머가 정말 멈췄는가"를 확인하는 데 쓴다.
- **실제 화면 시험**: 칸에 CPU 부하를 걸어(`yes > /dev/null`) 값이 오르는지, 디스크 값이 Finder와 1%p 안인지, MEM이 활동 상태 보기와 비슷한지, 확장·축소 때 수요가 바뀌는지.
- **이 Mac에 외부 디스플레이가 없을 때**: 다중 디스플레이 시나리오(§3.3 ①②③)는 규칙 시험(probe)과 `devdisplay`로 확인하고, 실제 연결 시험은 사용자에게 맡긴다고 릴리즈 노트에 적는다.
- **배포 전**: 배포 빌드로 위 §7.1을 모두 재고 결과를 릴리즈 노트(두 언어)에 넣는다.
