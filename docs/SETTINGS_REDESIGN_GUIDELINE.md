# 설정 창 개편 가이드라인 (디자인 · 검색 · 묶음 · 선택 방식 · 문구)

버전 1.4.9 (`main` 2b57cfc 이후) 기준. 이 문서는 **개편을 어떻게 할지 정한 계획서**다. 이 문서를 쓰는 동안 코드는 바뀌지 않았다. 단계마다 코드를 바꾸고, 합격 기준으로 판정하고, 사용자가 확인한 뒤 다음으로 간다.

구분: **[확인]** = 이 문서를 쓰며 코드를 읽거나 명령으로 확인한 사실, **[의심]** = 근거는 있으나 확인 못 함, **[미확인]** = 아직 보지 않음. 담당자는 [의심]과 [미확인]을 먼저 사실로 바꾼 뒤 고친다.

---

## 0. 결론

1. 설정 창은 **페이지 24개, 설정 키 119개**, 코드 약 2,950줄(`Sources/DynamicMacNotch/Settings/`)이다 [확인]. 부품(`SettingsComponents.swift`)과 규칙(`docs/ARCHITECTURE.md` "설정 화면 규칙")이 이미 있어서 **처음부터 다시 만드는 일이 아니라, 있는 부품을 한 단계 위로 올리는 일**이다.
2. 요청 6가지는 서로 의존한다. **인벤토리(전수 목록) → 묶음 → 선택 방식 → 문구 → 디자인 → 검색** 순서로 한다. 검색은 마지막에 해야 이름과 자리가 바뀐 뒤의 색인이 한 번에 맞는다.
3. 바뀌면 안 되는 것은 둘이다. **아이콘**(요청 1)과 **저장된 설정값**(키 이름·값 모양). 둘 다 자동 점검으로 막는다 (§1.2, §1.3).
4. 가장 먼저 풀 [확인]된 불일치: 고르는 부품을 안 쓰고 직접 쓴 `Picker`가 11곳, 같은 "표시 시간"인데 값 목록이 세 가지, 구역 설명 30개 중 100자를 넘는 것이 11개, 60자를 넘는 것이 22개 (§2).
5. 사용자 결정이 필요한 갈림길은 5개다 (§9). 각각 해당 단계 끝에서 **그림(스크린샷)을 보여 주고** 묻는다.

| 단계 | 이름 | 코드 변경 | 사용자 확인 | 결과물 |
|---|---|---|---|---|
| 0 | 기준선·트렌드 조사 | 없음 | 디자인 방향 | 기준 스크린샷, 측정값, 디자인 규칙 |
| 1 | 설정 인벤토리 | 없음(목록만) | 없음 | 항목 전수표, 중복·고아 목록 |
| 2 | 묶음 재정렬 | 있음 | **묶음안 승인** | 새 사이드바 구조 |
| 3 | 선택 방식 통일 | 있음 | 없음 | 부품 규칙 + 적용 |
| 4 | 제목·설명 문구 | 있음 | 문구 샘플 | 문구 규칙 + 적용 |
| 5 | 디자인 적용 | 있음 | **스크린샷 비교** | 새 모양 |
| 6 | 검색 | 있음 | 동작 확인 | 검색 + 색인 점검 |
| 7 | 마감·검증 | 없음 | 최종 확인 | 점검표 통과, 문서 갱신 |

다음 배포 번호는 규칙에 따라 **1.5.0**이다 (1.4.9 다음). 배포는 사용자가 요청할 때만 한다.

## 1. 지켜야 할 규칙 (모든 단계 공통)

### 1.1 작업 방식

| 규칙 | 이유 |
|---|---|
| 단계마다 커밋 하나. 빌드(`scripts/build.sh --dev`)와 probe 4종이 통과해야 다음 단계로 | 어느 단계가 문제인지 되돌리기 쉽게 |
| 작업은 `settings-redesign` 브랜치에서. 사용자가 확인하기 전에 `main`에 합치지 않음 | 개편은 되돌리기 어려운 폭이 큼 |
| `State(initialValue:)`를 쓴다 (`@State` 매크로 사용 불가). 글은 모두 `T("한국어", "English")` | 이 프로젝트의 빌드 환경 제약 |
| 최소 macOS 14 유지. macOS 26 전용 기능은 `#available(macOS 26.0, *)`로 감싸고 14·15에서는 대체 모양을 둔다 | 최소 버전 결정(1.4.8) |
| 설정 창은 **별도 프로세스(도우미)** 다. 본 앱에서 읽거나 부르는 값은 `Helper.sendToMain`을 거친다 | 설정 창 코드가 본 앱 메모리를 늘리지 않게 |
| 개발 빌드의 설정 시험은 키마다 따로 저장하고, 끝나면 키마다 읽어 확인한다. `bash` 3.2는 `declare -A` 없음 | 2026-11-09 복원 실패 사고 |
| 배포하지 않는다. 단계 7이 끝나도 사용자가 "배포"를 말할 때까지 로컬 커밋만 | 지침 |

### 1.2 아이콘은 그대로 (요청 1)

**[확인]** 아이콘은 두 곳에서 온다.
- `SettingsPage.symbol` ([SettingsPage.swift](../Sources/DynamicMacNotch/Settings/SettingsPage.swift)): SF Symbols 이름 24개.
- `SettingsIcon`·`BluetoothGlyph` ([SettingsView.swift](../Sources/DynamicMacNotch/Settings/SettingsView.swift)): 블루투스만 직접 그린 룬 기호.

| 바꾸지 않는 것 | 바꿔도 되는 것 |
|---|---|
| 기호 이름(`symbol` 표), 블루투스 직접 그림, 굵기 `.medium`, 사이드바 크기 13pt·카드 크기 22pt, 색(보통 강조색, 선택되면 흰색) | 아이콘 둘레의 간격, 줄 높이, 선택·호버 배경의 모양 |

- **아이콘 타일**(색 있는 둥근 네모 배경)은 아이콘 모양을 바꾸는 것으로 보고 **넣지 않는다.** 하고 싶으면 사용자에게 먼저 묻는다.
- 점검: DEV probe에 "기호 표 고정" 검사를 넣는다. 24개 `symbol` 값을 문자열로 박아 두고 비교한다. 페이지를 합치거나 옮겨도 각 페이지의 기호는 그대로 따라가야 한다. 합쳐서 사라지는 페이지가 있으면 그 사실을 사용자에게 알린다.

### 1.3 저장된 설정은 건드리지 않는다

- `@Setting("키", default:)`의 **키 이름과 값의 모양(자료형, enum rawValue)** 은 바꾸지 않는다. 화면이 바뀌어도 사용자의 기존 설정이 그대로 적용돼야 한다.
- 점검: 단계 시작과 끝에 `settings.settingKeys`를 파일로 뽑아 `diff`가 비어야 한다. 키를 지워야 하면 사유와 함께 사용자에게 묻고 `AppSettings`의 옛 키 정리 목록에 넣는다 (1.4.2에서 옛 이름 키를 지운 방식 그대로).
- 값 목록(`ValueMenu`)을 줄이거나 바꿀 때: **저장돼 있을 수 있는 옛 값이 새 목록에 없으면 선택 칸이 비어 보인다.** 새 목록은 옛 목록을 포함하거나, 가장 가까운 값으로 옮기는 코드를 같이 넣는다. probe에 "기본값과 옛 값이 목록에 들어 있다" 검사를 둔다.

### 1.4 성능

- 설정 창이 열려 있는 동안 **새 타이머·폴링을 만들지 않는다.** 검색도 키 입력에 반응만 한다.
- 본 앱의 대기 CPU·메모리는 개편 전후로 같아야 한다 (기준: 실행 직후 17.8MB, 대기 0.23~0.27%, `release-idle.sh`).

## 3. 단계 0 — 기준선·트렌드 조사 (코드 변경 없음)

**목표:** "트렌디하다"를 감이 아니라 **적용할 규칙 목록**으로 바꾼다 (요청 6).

**할 일**
1. **기준 스크린샷**: 24개 페이지 × 한국어·영어 × 라이트·다크 = 96장. `DMN_SETTINGS_PAGE=<페이지>`로 페이지를 열고 설정 창 한 장만 찍는다 (전체 화면 캡처 금지). 설정 창 모양의 흐림·투명도 기본값과 극단값(투명도 0.9)에서 각 1장씩 더. 저장 위치 `build/audit/settings-before/`.
2. **측정**: 설정 창을 열고 60초 대기한 도우미 프로세스의 메모리·CPU, 페이지 24개를 한 번씩 오갈 때의 메모리 증가. 본 앱의 `release-idle.sh` 값도 같이 적어 둔다.
3. **트렌드 조사**: 다음 순서로 근거를 모은다. 기억에 의존하지 말고 출처를 문서에 적는다.
   - Apple Human Interface Guidelines: macOS 26(Tahoe)의 Liquid Glass 사용 원칙(유리는 탐색·조작 층에, 내용 층에는 겹쳐 쓰지 않는다), 사이드바·검색 필드·폼·행의 규격.
   - macOS 26 **시스템 설정** 앱을 직접 열어 본 구조: 사이드바 맨 위 검색, 묶음 머리글, 둥근 카드형 묶음, 행의 제목 + 보조 설명 + 오른쪽 컨트롤 배치, 행 높이, 모서리 반지름(동심원 규칙).
   - 같은 종류의 최신 앱(예: 시스템 설정, Xcode 설정, 잘 만든 메뉴바 앱) 3~4개의 설정 화면 스크린샷 비교.
4. **프로젝트에 맞춘 조정 목록**을 적는다. 적어도 다음은 판단한다:
   - 이 창은 **테두리 없는 투명 창**이고 사용자가 흐림·투명도를 바꾼다. 글자 대비가 투명도 0.9에서도 유지돼야 한다.
   - 최소 macOS 14에서는 `glassEffect`가 없다. 14·15의 대체 모양(얇은 머티리얼)을 정한다.
   - 창은 860×620 고정 최소 크기. 사이드바가 길어지면(§5) 크기를 바꿀지 판단한다.

**결과물:** `docs/SETTINGS_DESIGN_RULES.md`(새 문서, 1~2쪽): 간격표(4pt 단위), 모서리 반지름, 글자 크기 계층, 색 토큰, 행·카드 규격, 라이트·다크 규칙, 14·15 대체 모양. 이후 단계는 이 문서만 보고 모양을 정한다.

**합격 기준:** 규칙마다 "무엇을, 왜, 어디서 확인했는지"가 한 줄씩 있다. 사용자에게 **디자인 방향을 한 번 확인**받는다 (§9-②).

## 4. 단계 1 — 설정 인벤토리 (코드 변경 없음)

**목표:** 119개 키가 어느 페이지의 어느 줄에서 바뀌는지 한 표로 만든다. 이후 모든 단계(묶음·통일·문구·검색)의 원자료다.

**할 일**
1. `AppSettings.settingKeys`와 각 페이지의 `$settings.<이름>` 사용처를 맞춰 표 `docs/SETTINGS_INVENTORY.md`를 만든다. 열: 키, 현재 페이지·구역, 제목(한/영), 컨트롤, 선택지 수, 기본값, 딸린 항목(`Indented`/`disabled` 조건), 설명 글자 수.
2. 분류해서 표시한다.
   - **화면에 없는 키**(내부 상태): 창 위치, 홈 순서 같은 것. 검색 대상에서 제외할 **명시 목록**이 된다.
   - **화면에 두 번 나오는 키**: 단계 0의 H [의심]을 여기서 확인한다.
   - **죽은 설정**: 읽는 코드가 없는데 화면에는 있는 것.
   - **홈에 페이지 표시** 스위치처럼 다른 페이지의 값을 대신 바꾸는 줄(`HomePageToggle`).
3. 표를 만드는 스크립트는 `.private/tools/`에 두고(공개 저장소에 올리지 않음), 표 자체는 `docs/`에 둔다.

**합격 기준:** 119개 키가 전부 "화면의 한 줄" 또는 "화면 밖 목록"으로 분류돼 있고, 분류 안 된 키가 0개다. 이 표는 단계 6의 색인 검사에서 그대로 쓴다.

## 5. 단계 2 — 묶음 재정렬 (요청 3)

**원칙:** 사용자가 "무엇을 하고 싶은지"로 찾는다. 코드 구조(알림·상시 표시)나 만든 순서가 아니다.

  디스플레이       노치를 띄울 화면, 디스플레이별 알림·상시 표시, 전체 화면

## 6. 단계 3 — 선택 방식 통일 (요청 4)

**목표:** 같은 종류의 옵션은 어디서나 같은 방식으로 고른다. 그리고 **규칙을 어기면 빌드나 점검에서 걸리게** 한다.

### 6.1 규칙 (현재 `ARCHITECTURE.md` 표를 구체화)

| 값의 종류 | 부품 | 기준 |
|---|---|---|
| 켜기·끄기 | `Toggle` | 항상 오른쪽 스위치. 체크박스 사용 안 함 |
| 종류 고르기 | 선택지 **2~3개** + 글이 짧음(한국어 각 6자·영어 각 10자 이하) → `SegmentedChoice` | 3개라도 글이 길면 아래로 |
| | 선택지 **4개 이상**이거나 글이 길거나 **기기·서비스처럼 목록이 변함** → `MenuChoice` | 지금 `MonitorMetric`(6개)·`MonitorExpand`(4개)가 여기 |
| 시간·개수·크기의 **정해진 값** | `ValueMenu` | 값 목록은 `Choices` 한 곳에서 이름 붙여 가져온다 (아래) |
| **연속된 값**(눈으로 보며 조절) | `ValueSlider` | 명도·투명도·길게 누르기 시간처럼 |
| 쉼표 목록 / 폴더 | `ListField` / `FolderSetting` | 그대로 |
| 서로 배타인 두 칸(왼쪽/오른쪽) | `MenuChoice` 한 쌍 | 한쪽이 고르면 다른 쪽에서 비활성 (이미 있음, 유지) |

### 6.2 할 일

1. **직접 쓴 `Picker` 11곳**(§2.2-A)을 표 규칙에 따라 부품으로 바꾼다. 선택지가 enum이 아닌 것(기기·서비스 목록)은 `MenuChoice`가 받을 수 있게 **문자열 목록용 부품**(`ListChoice`)을 추가한다. `.pickerStyle(.segmented)`를 쓰는 3곳은 규칙에 따라 `SegmentedChoice`로 옮기거나 `MenuChoice`로 바꾼다.
2. **값 목록을 한곳으로**(§2.2-B): `enum Choices { static let duration = [...], percent, memoryLimit, refresh... }` 같은 이름 붙은 목록을 `SettingsComponents.swift`에 두고, 표시 시간은 **한 목록**을 쓴다. HUD가 1.0초를 따로 가지는 이유가 있으면(짧게 스치는 HUD) 이유를 주석에 적고, 없으면 합친다. §1.3의 옛 값 규칙을 지킨다.
3. **퍼센트·초·MB 형식**을 `Format`(또는 `L10n`)의 함수 하나씩으로 (§2.2-C).
4. **종속 행의 모양**을 하나로: 위 스위치가 꺼지면 아래 줄은 흐리게(`disabled`) + 들여쓰기(`Indented`). 지금은 `SettingsSection(disabled:)`와 `Indented(enabled:)`와 `.disabled()`가 섞여 있다. 어느 쪽이든 **왜 꺼졌는지**(예: "음량 HUD가 꺼져 있어요")를 보조 설명으로 한 번 보여 준다.
5. **강제 장치**: `scripts/`에 간단한 검사 하나를 둔다 — `Settings/Pages/` 안에 `Picker(`·`Toggle(` 직접 사용이 없어야 하고(`Toggle`은 부품으로 감싸거나 허용 목록), 새로 생기면 빌드 후 점검에서 실패. DEV probe에 "모든 `SettingOption`이 규칙에 맞는 부품으로 쓰인다"(선택지 수 대비 부품)를 넣는다.

**합격 기준**
- 직접 쓴 `Picker` 0개 (현재 11개). 같은 이름의 줄(예: "표시 시간")은 모든 페이지에서 같은 값 목록과 같은 부품.
- probe 4종 통과, 설정 probe의 검사 수가 늘고 실패 0. 키 `diff` 없음.
- 모든 부품이 키보드(Tab·Space·화살표)로 조작되는지 샘플 5개 확인 [미확인].

## 7. 단계 4 — 제목·설명 문구 (요청 5)

### 7.1 글 규칙

3. 영어: 줄 이름은 첫 글자만, 구역 제목·버튼은 Title Case (지금 규칙 유지). 영어가 한국어보다 길어 잘리는 줄이 없는지 단계 0의 스크린샷 방식으로 확인한다.

5. **색:** 강조색 하나 + 의미색(켜짐 초록, 주의 주황)만. 라이트·다크 모두. 흰색 층 위의 대비.
6. **움직임:** 페이지 전환, 접기·펴기는 `snappy` 0.25초 하나로 통일 (지금 사이드바와 같은 값). 시스템 "동작 줄이기" 설정이 켜지면 끈다.
7. **상태:** 비활성 줄의 흐림 정도 한 가지, 오류·권한 필요 표시는 한 컴포넌트(`StatusText` 확장).
8. **macOS 14·15 대체:** `#available(macOS 26.0, *)` 밖에서는 `.ultraThinMaterial`과 얇은 테두리. 새 부품마다 두 모양을 같이 만든다.

## 10. 단계 6 — 검색 (요청 2)

**목표:** 설정 창 어디서든 키워드로 **모든 설정**을 찾아 그 줄로 이동한다.

### 10.1 동작

- 사이드바 맨 위(창 버튼 40pt 아래)에 검색 필드. `⌘F`로 포커스, `Esc`로 비우고 원래 페이지로.
- 입력하면 오른쪽 영역이 **결과 목록**으로 바뀐다: 줄 이름, 보조 설명 일부, 경로(`묶음 › 페이지 › 구역`), 검색어 강조.
- 결과를 누르거나 `Return`: 그 페이지로 이동 → 그 줄까지 스크롤 → **1.2초 강조**. 위·아래 화살표로 결과를 고른다.
- 결과가 없으면 빈 상태 글("'xxx'에 맞는 설정이 없어요") 한 줄과 비슷한 낱말 제안은 하지 않는다 (불필요).
- 검색은 **현재 앱 언어와 상관없이 한국어·영어 둘 다** 맞춘다 (사용자가 영어 이름을 외워 두었을 수 있음).
- 한국어는 **NFC로 정규화**해서 비교한다(조합 중인 글자·자모 분리 문제). 초성 검색(ㅅㅅㄹ)은 선택 사항: 규칙이 간단하고 색인이 작으니 넣어도 좋다.
- **동의어**를 색인에 넣는다: 음량 = 볼륨 = volume, 와이파이 = Wi-Fi, 밝기 = brightness, 투명 = transparency = 흐림 = blur, 알림 = alert, 상시 = live = 고정 등. 목록은 단계 1의 표에서 줄마다 1~3개.

### 10.2 색인의 구조

화면에 아직 그려지지 않은 페이지의 줄은 SwiftUI가 알려 주지 않는다. 그래서 **색인은 코드에 있는 목록**이어야 한다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 줄마다 `SettingsRow(id:)`로 선언하고, 페이지마다 그 줄 목록(`static let rows: [SettingsEntry]`)을 가진다 | 줄과 색인이 한 파일 안에 있어 같이 고치기 쉬움 | 줄을 빼먹을 수 있음 → 점검으로 막음 |
| 색인 파일을 따로 둔다 | 한곳에서 보임 | 줄 이름을 고치고 색인을 안 고치기 쉬움 |

**권고: 위 방식.** `SettingsEntry`는 `id`(= `페이지.키`. 키 4개는 두 페이지에 나오므로 키만으로는 겹친다 — 인벤토리 §1-③), 한/영 제목, 한/영 보조 설명, 동의어, 소속 페이지·구역을 가진다.

### 10.3 색인 점검 (DEV probe에 추가)

1. 단계 1의 표에서 "화면에 있는 키" 117개가 모두 색인에 **한 줄 이상** 있다. **빠진 키 0개.** 화면 밖 키는 명시 목록(`onboardingDone`)에 있다.
2. 색인의 `id`가 중복되지 않는다. 색인의 모든 페이지가 `SettingsPage`에 있다.
3. 색인의 제목이 실제 줄의 제목과 같다: 모든 페이지를 화면 밖 뷰(`NSHostingView`)로 만들어 `SettingsRow`가 등록하는 제목을 모아 색인과 비교한다 [미확인: 화면 밖 렌더링으로 등록이 되는지. 안 되면 소스 문자열 비교로 대체].
4. 검색 함수 시험: "volume"·"볼륨"·"음량"이 같은 줄을 찾는다, 한국어 NFD 입력도 찾는다, 빈 입력은 결과 없음, 모든 항목이 자기 제목으로 검색된다 (119개 전부).
5. 이동 시험: 결과를 열 때 `page`가 바뀌고 `scrollTo(id)`가 불린다. `Form`/카드에서 `ScrollViewReader.scrollTo`가 실제로 그 줄까지 가는지 샘플 5개를 눈으로 확인 [미확인].

### 10.4 성능

- 색인은 약 120개 문자열이라 **디바운스·백그라운드 처리 불필요.** 키를 칠 때마다 걸러도 1ms 안팎이어야 한다 (DEV에서 측정해 기록).
- 검색 때문에 새 타이머·관찰자를 만들지 않는다. 설정 창을 닫으면 색인 상태를 버린다.

**합격 기준:** §10.3의 1~4가 probe로 자동 통과, 5는 눈으로 5건 확인. 검색 입력이 한 글자씩 들어갈 때 화면이 끊기지 않는다.

| 자원 | 설정 창 60초 대기 CPU·메모리, 24페이지 순회 시 메모리, 본 앱 `release-idle.sh` | 단계 0 기준과 같음, 누수 0 |
| 문서 | `ARCHITECTURE.md` "설정 화면 규칙" 표·용어, `SETTINGS_DESIGN_RULES.md`, `SETTINGS_INVENTORY.md`, `.private/PROJECT_CONTEXT.md` | 새 구조와 일치 |

배포 전에는 지금까지의 배포 전 시험(1.4.9와 같은 목록: 배포 빌드 대기 측정, 380회 스트레스, probe, 경고 0, 문자열 검사)을 그대로 하고, 릴리스 노트에 한/영 표로 결과를 적는다. 노트에는 **바뀐 위치 안내**(예: "일반의 노치 조작이 '노치 → 노치 조작'으로 옮겨졌습니다")를 꼭 넣는다 — 설정이 사라졌다고 오해하지 않게.

## 12. 위험과 대비

| 위험 | 대비 |
|---|---|
| 화면을 고치다 저장된 설정이 어긋남 | §1.3: 키 `diff`, 옛 값 목록 검사 |
| 페이지를 옮겨서 다른 코드가 옛 페이지 이름을 부름 (`openPermissions` 등) | 단계 2 합격 기준의 `grep`, `DMN_SETTINGS_PAGE` 시험 |
| 직접 만든 카드가 접근성을 잃음 | §8 B안은 접근성 점검 통과가 조건, 아니면 A안 |
| 검색 색인이 화면과 어긋남 | §10.3의 3번 자동 점검, 줄과 색인을 한 파일에 둠 |
| 투명 창에서 글자가 안 보임 | 극단값 대비 시험을 단계 5·7에 넣음 |
| 영어 글이 길어 잘림 | 영어 스크린샷 전수 확인 |
| 개편이 너무 커서 한 번에 못 끝냄 | 단계마다 커밋·확인. 단계 2~4는 서로 독립이라 하나가 막혀도 이전 단계 결과는 유지 |
| 사용자가 익숙한 위치가 바뀜 | 릴리스 노트의 위치 안내, 검색으로 옛 이름도 찾기(동의어에 옛 이름 포함) |
