# 노치 AI 채팅 — 첨부 파일과 출력 형식 가이드라인

작성: 2026-11-06 · 설계만 (구현 전) · 대상 버전 제안: 1.4.0

세 가지를 다룬다. ① 이미지·문서 첨부를 넣되 메모리가 늘지 않게 하는 방법, ② 표와 목록 사이드바가 불편한 문제, ③ 노치에 맞지 않는 출력 형식을 피하게 하는 내부 지침 개정안.
수치는 모두 이 Mac(Apple Silicon, macOS 27.3)에서 직접 잰 값이거나 각 회사 공식 문서에서 확인한 값이다. 확인하지 못한 것은 "미확인"이라고 적었다.

---

## 0. 결론

1. **첨부는 넣을 수 있고, 메모리 문제는 구조로 풀 수 있다.** 핵심은 세 가지다.
   - 이미지를 줄이는 일(디코딩·축소·재인코딩)을 **본 앱이 아니라 짧게 떴다 사라지는 도우미 프로세스**에서 한다. 이미 스크린샷 썸네일에 쓰는 `ImageTool` 방식이다. 도우미가 끝나면 메모리가 통째로 돌아간다.
   - 요청 본문은 **파일에 조금씩 써서 파일째 보낸다.** 원본·base64·JSON을 메모리에 올리지 않는다. 30MB 문서가 112.7MB → 2.8MB가 된다 (§1).
   - 첨부는 **그 질문에만** 보내고, 대화 기록에는 이름만 남긴다. 바이트를 저장하지 않으니 오래 써도 쌓이지 않는다.
2. **표는 노치에서 읽기 어렵고, 3열부터는 실제로 깨진다.** 같은 문제는 목록을 열면 더 심해진다 (본문 폭 340pt → 222pt). 권장은 **프롬프트로 표를 막고(A), 그래도 오는 표는 앱이 항목 목록으로 바꿔 보여 주는 것(B)**이다. 표를 예쁘게 그리는 쪽(가로 스크롤, 확대 창)은 비용 대비 효과가 낮다.
3. **출력 형식 지침 개정안**은 §3.4에 있다. 표·제목·수평선·인용·체크박스·이미지·HTML·각주를 쓰지 않고, 코드는 짧게, 답은 결론부터 쓰게 한다.

이 문서가 정하지 않은 것은 §5에 모았다.

## 1. 측정 근거 — 메모리가 얼마나 드는가

독립 실행 도구로 같은 파일을 단순한 방식과 제안 방식으로 처리해 비교했다. 표의 "최고"는 `ri_lifetime_max_phys_footprint`다. 프로세스 기본값(약 2MB)이 들어 있다. **앱에 넣은 뒤의 값은 아직 재지 않았다.**

### 1.1 이미지

| 입력 | 단순 방식(`NSImage`로 열어 다시 저장) 최고 | 제안 방식(ImageIO 썸네일 1568px → JPEG 0.8) 최고 | 보낼 크기 |
|---|---|---|---|
| 사진 4032×3024, 8.9MB | 143.7 MB | **38.9 MB** | 0.75MB (base64 1.0MB) |
| 스크린샷 PNG 3024×1964, 6.7MB | 87.8 MB | **38.8 MB** | 0.75MB |
| 큰 사진 8000×6000, 37.5MB | **536.2 MB** | **66.0 MB** | 0.50MB |
| 입력 칸 미리보기 96px | — | +1.8 MB (최고 4.4 MB) | 수십 KB |

- 단순 방식은 전체 해상도를 비트맵으로 풀어서 사진 한 장에 100~500MB를 쓴다.
- 제안 방식은 원본보다 작은 크기로만 디코딩한다. 그래도 38.9~66MB가 순간적으로 필요하다. **이 값은 본 앱이 아니라 도우미가 쓰고, 도우미가 끝나면 전부 반환된다.**
- 같은 프로세스에서 10장을 반복하면 차이가 크다.

| 10장 반복 (한 프로세스) | 처리 중 | 결과를 버린 뒤 |
|---|---|---|
| 전체 해상도로 처리 | 87.8 MB (최고 173.7 MB) | **87.8 MB — 그대로 남음** |
| 1568px로 줄여 처리 | 14.7 MB (최고 47.7 MB) | 14.7 MB |

해제한 메모리가 돌아오지 않는다. 이 앱의 메모리 지킴이가 만들어진 이유와 같은 현상이고, **도우미 프로세스를 쓰는 근거**다.

### 1.2 문서와 요청 본문

| 작업 | 단순 방식 최고 | 제안 방식 최고 |
|---|---|---|
| 30MB 파일 → 요청 본문(base64+JSON 40.6MB) | 112.7 MB (읽기 32 → base64 72 → JSON 112.7) | **2.8 MB** (192KB씩 읽어 base64로 파일에 씀) |
| 100MB 파일 → 본문 133MB | (측정 안 함. 30MB 결과를 비례하면 약 370MB) | **2.8 MB** |
| 파일로 보내기 `uploadTask(fromFile:)`, 40MB | — | 10.0 MB (네트워크 기본값 포함, 파일 크기와 무관) |
| PDF 100쪽 쪽수·첫 쪽 미리보기 | — | 7.2 MB |
| PDF 100쪽 **글자 전부 추출** | 55.5 MB (35만 자) | **하지 않는다** |

- 읽는 단위를 줄일수록 작아진다: 3MB 9.9 / 768KB 5.4 / **192KB 2.8** / 48KB 2.2 MB. 192KB를 쓴다.
- PDF는 앱이 글자를 뽑지 않고 **원본을 그대로** 보낸다. 세 회사 모두 PDF를 직접 읽는다 (§2.1).
- `URLSession.bytes(for:)`(현재 SSE 읽기 방식)에는 `httpBodyStream`으로 파일 스트림을 주는 방법이 있다. **동작은 구현할 때 100MB로 확인해야 한다 (미확인).**

### 1.3 개인정보

사진을 줄여 다시 저장하면 **GPS 위치·카메라 기종·Exif 코멘트가 모두 사라진다** (원본에 넣은 값이 재인코딩 뒤 없어짐을 확인). 첨부 이미지는 항상 이 경로로 처리한다.

## 2. 첨부 기능 설계

### 2.1 서비스별 한도 (공식 문서 기준)

| | Claude | GPT (Responses API) | Gemini |
|---|---|---|---|
| 이미지 형식 | JPEG·PNG·GIF·WebP | PNG·JPEG·WebP·GIF(움직이지 않는 것) | PNG·JPEG·WebP·HEIC·HEIF |
| 이미지 크기·수 | 장당 10MB(base64), 8000×8000px, 요청당 100장(컨텍스트 200k 모델) | 요청 합계 512MB, 1,500장 | 인라인은 요청 전체 20MB, 3,600장 |
| PDF | 요청 128MB, 600쪽(1M 컨텍스트 미만이면 100쪽) | 파일당·요청 합계 50MB | 50MB 또는 1000쪽 |
| 문서 형식 | PDF와 평문(txt·csv·md는 Files API로만). **docx·xlsx 불가** | PDF, docx, xlsx, pptx, csv, md, json 등 | PDF, docx, pptx, xlsx, txt, md, html 등 |
| 이미지 토큰 | 28×28px 조각마다 1토큰, 긴 변 1,568px(4.7 이후 모델은 2,576px·최대 4,784토큰) | 모델마다 패치(32px)·타일(512px) 방식 | 768px 타일마다 258토큰 |
| PDF 토큰 | 쪽당 텍스트 1,500~3,000 + 쪽 이미지 비용 | 텍스트 + 쪽 이미지 | 쪽당 258 |

출처: [Claude 이미지](https://platform.claude.com/docs/en/build-with-claude/vision) · [Claude PDF](https://platform.claude.com/docs/en/build-with-claude/pdf-support) · [OpenAI 파일 입력](https://developers.openai.com/api/docs/guides/file-inputs) · [OpenAI 이미지](https://developers.openai.com/api/docs/guides/images-vision) · [Gemini 문서](https://aistudio.google.com/docs/document-processing) · [Gemini 이미지](https://aistudio.google.com/docs/image-understanding)

**문서끼리 엇갈리는 값:** Gemini 인라인 한도는 이미지 문서에 20MB, [Google 발표](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-api-new-file-limits/)에 100MB로 나온다. 가장 작은 쪽(20MB)에 맞춘다. 검색 중 보인 "Claude 이미지 5MB"는 Amazon Bedrock 한도이고, 직접 API는 10MB다.

### 2.2 앱의 자체 상한 (제안)

세 서비스를 모두 통과하는 값으로 잡는다. 노치는 가볍게 쓰는 용도라 서비스 한도보다 훨씬 낮게 둔다.

| 항목 | 상한 | 이유 |
|---|---|---|
| 이미지 | 질문당 4장, 원본 파일 20MB 이하 | 줄여서 보내므로 원본 크기는 처리 시간·도우미 메모리(최대 66MB) 때문에만 제한 |
| PDF | 질문당 1개, 10MB 이하, 30쪽 이하 | 쪽마다 1,500~4,500토큰이라 30쪽이면 Claude에서 약 9만~13만 토큰. Haiku 5.5($0.10/백만 토큰)면 1센트 안팎이지만 Opus 5.5($4)면 약 0.4~0.5달러 |
| 텍스트 파일 | txt·md·csv·json·코드 200KB 이하, 합계 400KB | 앱이 UTF-8로 읽어 **질문 앞에 붙인다.** 서비스 차이가 없고 Claude의 문서 블록 제약도 피한다 |
| 요청 본문 전체 | 18MB 이하 | Gemini 인라인 20MB 안쪽 |
| docx·xlsx·pptx | 1차 제외 | Claude가 못 읽는다. 2차 후보 (GPT·Gemini에서만 켜기) |

### 2.3 처리 흐름 (메모리 규칙)

```
선택(붙여넣기·끌어놓기·클립 버튼)
  → 본 앱: 파일 크기·종류만 확인 (stat, UTType). 바이트는 읽지 않는다
  → 도우미 프로세스(--attach=…): 이미지 축소·재인코딩 / PDF 쪽수·첫 쪽 미리보기
       결과: 임시 폴더(0700)의 JPEG 또는 PDF 사본(0600) + 96px 미리보기(수십 KB)
  → 본 앱: Attachment{ id, 이름, 종류, 바이트 수, 임시 파일 경로, 미리보기 }만 쥔다
보내기
  → BodyWriter: JSON 조각 + 첨부 base64를 192KB씩 임시 본문 파일에 쓴다
  → 파일 스트림으로 전송 (재시도는 같은 본문 파일 재사용)
  → 응답이 끝나면 본문 파일과 첨부 임시 파일 삭제
```

- **본 앱이 쥐는 것은 이름·경로·96px 미리보기뿐**이다. 첨부 1개당 수십 KB.
- 서비스별 본문 모양만 다르다: Claude `image`/`document` 블록(base64), GPT `input_image`(data URL)·`input_file`(`file_data`), Gemini `inlineData`. BodyWriter 하나로 세 가지를 만든다.
- 임시 파일은 보내기 완료·취소·새 채팅·앱 시작 시 지운다. **캐시 비우기도 첨부 폴더를 지운다.**
- 투명 PNG는 PNG로 유지하고, 그 밖의 이미지는 JPEG 0.8로 바꾼다. HEIC는 JPEG로 바꿔 세 서비스 모두 받게 한다.
- 이미지 긴 변은 **1568px**을 권장한다 (글자가 많은 스크린샷도 읽히고 Claude 기준 이미지당 약 1,500~2,400토큰). 더 싸게 쓰려면 1024px(약 1,000토큰)도 후보다.

### 2.4 대화 기록과 재전송

API는 상태가 없어서 이전 첨부를 다시 보내야 문맥이 이어진다. 장시간 사용에서 메모리와 비용을 가장 크게 키우는 지점이다.

| 방식 | 장점 | 단점 |
|---|---|---|
| **A. 그 질문에만 첨부 (권장 기본)** | 가장 단순·저렴, 임시 파일이 금방 사라짐, 프라이버시 좋음 | 후속 질문에서 모델이 이미지를 다시 보지 못함. 앞선 답변은 글로 남아 있음 |
| B. 최근 2번의 질문까지 다시 첨부 | "아까 그 그림에서…" 가능 | 질문마다 토큰·전송량 증가, 임시 파일 유지 |
| C. 서비스의 Files API에 올려 `file_id` 참조 | 재전송 없음 | 파일이 회사 서버에 남음(Gemini는 48시간). 삭제·안내 필요 |

권장은 **A를 기본으로 하고, 칩에 "다음 질문에도 포함" 토글을 두어 B를 선택할 수 있게** 하는 것이다. C는 개인정보 부담이 있어 제외한다.
저장된 대화(`Chats/<id>.json`)에는 **첨부 바이트를 넣지 않고** `📎 이름 (종류, 크기)` 한 줄만 남긴다. 다시 열면 첨부는 복원되지 않는다고 표시한다.

### 2.5 UI

- **입력 줄 위에 칩 한 줄:** 48pt 미리보기 + ✕, 최대 4개. 노치 높이는 입력 칸이 늘어날 때 쓰는 `chatInputExtra` 방식으로 한 줄(약 36pt)만 더한다.
- **들어오는 길 세 가지**
  1. 입력 칸에서 ⌘V — 클립보드에 이미지·파일이 있으면 첨부, 글자면 기존 동작.
  2. 채팅 페이지가 열려 있을 때 파일 끌어놓기 — 페이지 전체가 "여기에 놓아 첨부" 영역이 된다. 지금은 파일을 끌면 에어드랍·트레이 칸이 열리므로 **채팅 페이지에서만** 바꿔야 하고, 기존 동작과의 충돌은 구현 때 확인한다.
  3. 입력 줄 왼쪽 클립 버튼 — 기존 파일 선택 창을 재사용.
- **자동 첨부 금지 유지.** 클립보드·화면·파일을 앱이 알아서 붙이지 않는다. 사용자가 직접 고른 것만 보낸다.
- **오류 문구**를 정해 둔다: 크기 초과, 지원하지 않는 형식, 쪽수 초과, 모델이 이미지를 받지 못함(GPT·Gemini는 모델마다 다름, 사전 판별 불가라 400 응답을 안내로 바꾼다).
- 설정 안내문과 README의 개인정보 설명에 "첨부한 이미지·문서는 선택한 회사로 전송되고, 사진의 위치 정보는 지워서 보낸다"를 추가한다.

## 3. 표와 출력 형식

### 3.1 현재 모습 (개발 빌드에서 직접 확인)

- 화면 크기: 노치 본문 폭 **340pt**, 목록을 열면 **약 222pt**. 한 번에 보이는 답변 영역은 높이 약 110pt, **5줄 안팎**이다.
- 표는 `탭 90pt 간격`으로 그린다. 2열(180pt)은 목록을 열어도 읽힌다. **3열(270pt)부터 목록을 열면 넘치고, 4열(360pt)은 목록이 닫혀 있어도 겹친다.** 4열 표에서 셀이 서로 섞여 읽을 수 없었고, 목록을 열면 머리글 "PDF 한도"가 두 줄로 깨졌다.
- 행이 3~4개만 되어도 한 화면을 넘어 스크롤해야 한다.

### 3.2 해결안 비교

| 안 | 내용 | 판단 |
|---|---|---|
| **A. 프롬프트로 표 금지** | 표 대신 항목당 한 줄 목록으로 쓰게 한다 | **채택.** 구현 몇 줄, 효과 큼. 모델이 가끔 어길 수 있음 |
| **B. 앱이 표를 목록으로 변환 (안전망)** | 표가 와도 항목 카드 목록으로 바꿔 그린다 | **채택.** 파서가 이미 표의 머리글·행을 구분하므로 `ChatMarkdown`에 변환 규칙만 추가한다 |
| C. 가로로 스크롤되는 표 | 폭이 넘으면 옆으로 민다 | 비추. 텍스트 뷰 안에 별도 스크롤 뷰가 필요하고, 노치에서 가로 스크롤은 어색하다 |
| D. "표 크게 보기" 별도 창 | 노치 밖에 표 전용 창 | 비추(2차 후보). 노치 밖 창은 이 앱의 방향과 맞지 않고 구현이 크다 |
| E. 진짜 표(`NSTextTable`) | 열 맞춰 그림 | 해결 안 됨. 340pt에서 4열이면 열당 80pt라 한글 3~4자만 들어간다 |

**"현실적으로 불가능에 가깝나?"** 표를 노치에 보기 좋게 *그리는 것*은 그렇다. 하지만 표가 전하려는 *정보를 읽기 쉽게 보여 주는 것*은 A+B로 가능하다. 원본 Markdown은 복사 버튼으로 그대로 가져가므로 표가 필요하면 메모 앱 등에 붙여넣으면 된다.

변환 규칙 (B):

| 표 | 그리는 모양 |
|---|---|
| 2열 | `**항목**: 값` 한 줄씩 |
| 3열 이상 | 행마다 첫 칸을 굵게 한 줄, 아래에 `머리글: 값` 줄들 |
| 6열 초과·셀이 매우 긴 표 | 위와 같이 변환하되 앞의 8행까지만 보이고 "… 이하 N행은 복사로 확인"이라고 안내 |

### 3.3 그 밖에 노치에서 불편한 형식 (같은 방법으로 확인한 결과)

| 형식 | 노치에서의 모습 | 권장 |
|---|---|---|
| 제목(`#`) | 15/14/13pt 굵은 글씨로 세로를 많이 차지함 | 쓰지 않음. 굵은 글씨 한 줄로 |
| 중첩 목록 3단계 이상 | 들여쓰기가 폭을 먹어 글자가 좁아짐 | 2단계까지 |
| 코드 블록 | 긴 줄이 38자 안팎에서 줄바꿈되어 모양이 깨짐 | 핵심 10줄 이내, 줄당 38자 이내. 길면 말로 설명 |
| 긴 주소 | 3줄을 차지하지만 눌러서 열림 | `[제목](주소)` 형식만 (이미 지시함) |
| 체크박스 목록 `- [ ]` | 대괄호가 그대로 보임 | 쓰지 않음 |
| 이미지 `![]()` | 이미지는 사라지고 대체 글자만 남음 | 쓰지 않음 |
| HTML 태그·각주 | `<b>`와 `[^1]`이 원문 그대로 보임 | 쓰지 않음 |
| 수평선 `---` | 짧은 선이 공간만 차지함 | 쓰지 않음 |
| 인용 `>` | 들여쓰기 + 흐린 글씨 | 쓰지 않음 |
| 긴 답 | 5줄 보고 스크롤해야 함 | 결론을 첫 문장에, 150단어 안팎 |
| 수식 | 렌더링됨 | 허용, 짧게 (지금 지시 유지) |

앱 쪽 안전망(B와 같은 방식, 모델이 어겨도 읽히게): 제목은 본문 크기의 굵은 글씨로, 수평선은 그리지 않고, `- [ ]`/`- [x]`는 ☐/☑로, 이미지는 대체 글자만, HTML 태그와 각주 표기는 걷어 낸다.

### 3.4 내부 지침 개정안

현재(`ChatAPI.basePrompt`)의 형식 지시는 "제목과 표보다 짧은 문단을 선호"하는 정도라 표를 금지하지 않는다. 아래로 바꾸는 것을 제안한다. 날짜·검색·수식·링크 문단은 그대로 둔다.

```text
You are answering inside a small panel in a Mac's notch. Today's date is <date>.
The panel is about 40 characters wide and shows only 5 or 6 lines at a time, so the reader has to scroll.
Answer briefly and directly, in the language of the question. Put the answer or conclusion in the first
sentence, then add only the details that matter. Stay under about 150 words unless the user asks for more.

<검색 문단: 지금과 같음>

Format answers in Markdown, using only: short paragraphs, **bold**, *italic*, <u>underline</u>, `inline code`,
bullet or numbered lists nested at most two levels, and links written as [title](https://full-url).
Never use tables, headings, horizontal rules, block quotes, task-list checkboxes, images, HTML tags,
footnotes, or decorative emoji.
- Instead of a table or a comparison grid, write one bullet per item with the same facts in the same order,
  e.g. "- **Name**: value, value".
- Instead of a heading, write a short bold line.
- Show code only when it is short: a fenced block of at most 10 lines, each under 38 characters.
  Otherwise describe it in words.
- If the full answer would be long (long code, a long document, many rows), give a short summary and say
  you can continue in parts.
If the user explicitly asks for a table, write one with at most 3 columns and short cells.
Write all mathematics in LaTeX, using $...$ inline and $$...$$ for displayed equations. Don't write formulas in
plain text or Unicode, and don't put math in code blocks. Write a literal dollar sign as \$.
Keep displayed equations short and split long derivations across several $$...$$ blocks.
```

- 길이는 현재보다 약 120토큰 늘어난다. 질문마다 붙지만 비용 영향은 미미하다.
- 사용자가 설정에 적은 답변 지침은 지금처럼 이 뒤에 붙는다. 사용자가 표를 직접 요청하면 3열 이하로 허용하고, 그 표는 앱이 B 규칙으로 읽기 쉽게 바꿔 그린다.
- **서비스마다 지시를 따르는 정도가 다를 수 있다.** 같은 질문 20개(비교·요약·코드·설명)를 세 서비스에 보내 어긴 비율을 센다 (아직 하지 않았다). 통과 기준: 표·제목 사용 5% 이하. 남는 경우는 B가 처리한다.

### 3.5 목록 사이드바

목록을 열면 본문이 340pt에서 222pt로 줄어 위의 문제가 심해지고, 줄바꿈이 늘어 스크롤도 늘어난다.

| 안 | 내용 | 판단 |
|---|---|---|
| **1. 오버레이 (권장)** | 목록을 본문 위에 덮어 띄운다. 본문 폭은 그대로, 항목을 고르면 자동으로 닫힌다 | 구현이 작다 (`ChatPage.content`의 `HStack`을 `ZStack`으로). 목록은 "고르는 화면"이라 덮어도 불편이 적다 |
| 2. 목록을 열 때 노치 폭 확장 | 340 → 450pt | 페이지별 크기를 이미 지원해서 가능하지만, 노치가 목록을 열 때마다 커져 부담스럽다 |
| 3. 목록 폭 축소 | 1/3 → 아이콘+한 줄 제목 | 본문은 340 → 280pt 정도 확보. 제목이 잘려서 구분이 어렵다 |

권장은 1이다. 표는 A·B로 따로 해결하므로 목록의 폭과 무관하게 읽힌다.

### 3.6 시험 방법

- 형식 시험 사례 파일(표 4열·2열, 제목, 4단 중첩 목록, 인용, 체크박스, 긴 코드 줄, 긴 주소, 이미지·HTML·각주)을 모의 서버로 보내 **목록 열림/닫힘**에서 화면을 찍어 비교한다. 이 문서의 §3.1·3.3은 같은 방법으로 확인했다.
- 변환(B)은 `--chat-probe`에 렌더 명령을 추가해 폭·줄 수를 숫자로 확인하고, 화면 확인은 8개 사례 × 목록 2상태로 한다.
- 지침 시험은 §3.4의 20개 질문 × 3서비스.

## 4. 순서 제안

1. **먼저(작고 효과 큼):** §3.4 지침 개정 + §3.3의 안전망(제목·수평선·체크박스·HTML) + §3.2의 B(표 변환) + §3.5의 오버레이. 첨부 없이 출력 문제만 먼저 해결한다.

## 5. 결정이 필요한 것

1. 이미지 긴 변: 1568px(읽기 좋음, 권장) / 1024px(싸고 빠름).
2. 첨부 후속 질문 기본값: 그 질문에만(A, 권장) / 최근 2번의 질문까지(B).
3. 문서 범위: PDF + 텍스트 파일(권장) / docx·xlsx도 GPT·Gemini에서만 허용.
4. 앱 상한(§2.2)을 그대로 쓸지: 이미지 4장, PDF 10MB·30쪽 등.
5. 사용자가 표를 직접 요청했을 때: 3열 이하 허용 + 변환(권장) / 항상 목록으로.
6. 목록 사이드바: 오버레이(권장) / 폭 확장 / 폭 축소.
