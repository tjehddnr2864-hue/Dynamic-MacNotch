# 전체 점검 결과 기록

`AUDIT_GUIDELINE.md`의 단계별 결과를 여기에 쌓는다. 원자료(빌드 로그, probe 출력, 샘플)는 `build/audit/`에 있다(저장소에 넣지 않음).

## 요약 (1.4.2 → 1.4.3)

2026-11-10에 `AUDIT_GUIDELINE.md`의 0~9단계를 모두 마쳤다. 아래는 결론이고, 근거와 수치는 각 단계에 있다.

### 무엇을 찾았나

- **죽은 코드는 거의 없었다.** 설정 110개 중 안 쓰는 것 0개, 안 불리는 함수 0개.
- **누수는 없었다.** 반복 시험·1시간 시험·미리보기 스트레스 모두 앱 코드의 누수 0건.
- **문제는 "쓰는 동안 쓸데없이 하는 일"이었다.** Mac을 건드리지 않을 때는 조용하지만(CPU 약 0.2%), 쓰는 동안에는 여섯 곳이 필요 없이 돌았다.

### 고친 것

| 무엇 | 전 | 후 |
|---|---|---|
| 전역 마우스 감시: 화면 어디서든 마우스를 움직이면 모든 이동 이벤트를 받았다 | 움직이는 동안 약 27% | 노치에서 먼 곳은 0.9% (커서가 노치 근처일 때만 감시) |
| 네트워크 감시: AirDrop용 인터페이스가 바뀔 때마다 Wi-Fi·VPN 상태를 다시 읽었다 | 약 17초마다 35ms | 건너뜀 |
| Mission Control 점검: 창 목록 확인이 생각보다 비쌌고(약 3ms) 3초마다 돌았다 | 150초에 236ms | 약 33ms (10초마다, 이벤트 뒤 확인 0.6초) |
| 통화 감시: 통화와 무관한 알림 배너에도 화면 요소를 6번 훑었다 | 30초에 158ms | 150초에 19ms |
| AI 사용량: 노치를 숨겨도 계속 새로 읽었다 | 계속 | 숨긴 지 주기 한 번이 지나면 쉼 |
| 화면 녹화: 꺼도 1.5초 타이머가 깨어났다 | 계속 | 꺼지면 타이머 없음 |
| 숫자 설정 11개: 범위 방어가 없었다 | 손상된 값이 그대로 쓰임 | 읽을 때와 넣을 때 범위를 맞춤 |
| 새 홈 기능의 자리: 기존 사용자에게 맨 끝에 생겼다 | 맨 끝 | 기본 순서의 앞 항목 바로 뒤 (자원 사용량은 AI 사용량 다음) |

평소 사용 중 150초의 CPU는 0.64% → 0.15%가 되었다(마우스 감시를 고치기 전에 잰 값). Mac을 건드리지 않을 때는 1.4.2와 같다(0.2% 안팎, 18.5MB).

### 정리한 것

- 지움: 공개 전 이름의 설정 이전 코드, 중복된 스크린샷 저장 위치 읽기. 개발 전용 함수 3개는 배포 빌드에서 뺌.
- 나눔: 파일 5개 (`ActivityGlyphs`, `DownloadPage`, `DisplayNotchState+Sizes`, `CallAccessibility`, `MediaTypes`).
- 문서: README의 홈 페이지 수와 설정 페이지 이름, 코드 구조 안내의 감시기 규칙과 점검 도구, 디스플레이 가이드라인의 Mission Control 값.
- 안전망: 설정 probe 17건 → 45건.

### 확인 방법

- 자동: probe 4종(6,257 / 45 / 386 / 30건, 실패 0), 반복 시험, 미리보기, 1시간 시험.
- 직접(사용자): 확인 목록 18개 항목 모두 정상, 마우스 감시 수정 뒤 제스처·파일 끌기 재확인 정상.

### 남긴 것

- 스크린샷 썸네일을 끌 때의 메인 스레드 변환(드묾).
- `ChatStore`, `MediaController`, `DisplayNotch`의 분리(얽힘이 커서 이득보다 위험이 큼).
- 본 앱 → 설정 창 방향의 변경 알림(실제로 마주치기 어려움).
- 파일 끌기 뒤 시스템 쪽 누수 656바이트가 반복되는지 미확인.
- 커서가 노치 근처에서 움직이는 동안의 비용은 전과 같다.

위 8초 샘플에서 메인 스레드가 바빴던 시간의 대부분은 **창 서버 이벤트 수신**이었다(532 중 대부분, 미디어 표시는 꺼진 상태: 재생 소스가 Apple Music이라 브라우저 영상은 노치에 뜨지 않음). 즉 마우스를 계속 움직이거나 끄는 동안에는 전역 마우스 감시 때문에 앱이 **수 %**의 CPU를 쓴다. 단계 5에서 "이득은 최대 0.1% 안팎"이라고 적은 것은 마우스를 거의 움직이지 않던 구간의 값이라 **과소평가였다.** 정확한 값은 마우스를 움직이는 동안과 가만둘 때를 나눠 재야 하며(단계 8), 그 결과로 구조 변경 여부를 다시 정한다.

### 19. 마우스를 움직일 때의 CPU (A-003)

설치된 개인용 빌드, 사용자가 30초 동안 마우스를 계속 움직인 뒤 손을 뗌.

| 구간 | CPU |
|---|---|
| 마우스를 움직이는 30초 | **8.06초 (약 27%)** |
| 다시 잰 15초 (움직임) | 4.06초 (약 27%) |
| 손을 뗀 30초 | 0.05초 (0.17%) |

- 15초 샘플에서 앱 코드는 85ms뿐이었다(`DisplayNotch.installMonitors`의 처리 클로저). 나머지는 창 서버가 보내는 마우스 이동 이벤트를 받는 시스템 쪽 비용이다(메시지 수신, 이벤트 해독, `NSEvent` 생성).
- 원인은 전역 마우스 이동 감시(`Notch/DisplayNotch.swift:219`)다. 마우스가 화면 어디에 있든 모든 이동 이벤트가 이 앱으로 온다.
- 단계 5·7의 "이득은 작다"는 판단은 틀렸다. **A-003의 위험도를 중간 → 높음으로 올린다.** 조치는 사용자 결정.

### A-003 수정 (방법 B, 2026-11-10)
