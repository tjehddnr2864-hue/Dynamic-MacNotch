# 노치 — Mission Control 숨김과 다중 디스플레이 구현 가이드라인

작성: 2026-11-06 · 설계만 (구현 전) · 대상 버전 제안: 1.5.0(Mission Control), 1.6.0(다중 디스플레이)

두 기능의 구현 방향, 일어날 수 있는 충돌·오류와 해결 방법, 작동 방식을 정리한다.
수치는 이 Mac(MacBook Pro, Apple Silicon, macOS 27.3, 디스플레이 1대)에서 직접 잰 값이다. **디스플레이가 1대뿐이라 다중 디스플레이 동작은 직접 확인하지 못했고**, 그런 부분은 "미확인"이라고 적었다.

---

## 0. 결론

1. **Mission Control 숨김은 안전하게 만들 수 있다.** 판정 기준은 `WindowManager`가 소유한 **`Spaces Bar` 창**이 보이는지다. 앱 Exposé는 같은 `ExposeShieldWindow`를 쓰지만 `Spaces Bar`가 없어서, 쉴드 창만 보면 앱 Exposé를 Mission Control로 잘못 알게 된다 (§1.1).
2. **상시 감시(폴링)는 하지 않는다.** 창 목록을 한 번 읽는 데 0.17~0.65ms가 들어, 20Hz로 읽으면 CPU 1% 안팎이다 (현재 대기 CPU 0.12~0.2%). 대신 창 서버 이벤트(비공개)를 **"창 목록을 다시 확인하라"는 신호로만** 쓰고, 판정은 항상 창 목록으로 한다. 이벤트가 오지 않아도 느린 안전 점검이 바로잡는다 (§2.2).
3. **다중 디스플레이는 "공유 모델 1개 + 디스플레이별 화면 상태 N개"로 나눈다.** 미디어·트레이·메모·채팅·상시 표시 목록은 이미 하나뿐이라 "상호작용 결과가 모든 디스플레이에 적용"은 구조상 자연스럽게 된다. 새로 만들어야 하는 것은 디스플레이마다 따로 있는 **화면 상태(확장 여부·페이지·호버·눌림)**다 (§3.2).
4. **한 번에 확장되는 디스플레이는 1개로 제한한다.** 타이머·메모·채팅 입력·카메라가 모두 하나뿐인 객체라, 두 디스플레이에서 동시에 열면 충돌한다 (§3.5).
5. **먼저 Mission Control(작고 독립적), 그다음 디스플레이 계층 정리(동작 변화 없음), 마지막에 다중 디스플레이** 순서로 나눠 구현한다 (§4).
6. **확인이 필요한 해석이 7개 있다** (§6). 특히 마지막 옵션의 "선택한 상시 표시가 비활성화인 경우"를 어떻게 읽을지가 설계를 좌우한다.

## 1. 확인한 사실 (이 Mac에서 측정)

### 1.1 Mission Control의 창 신호

Mission Control을 `open -a "Mission Control"`과 키보드(⌃↑)로 열고 닫으며, 화면에 올라온 창의 변화를 기록했다.

| 상황 | 나타나는 창 | 판정 |
|---|---|---|
| 평소 | `Dock`의 `Wallpaper` 창만 | — |
| **Mission Control** | `WindowManager`의 **`ExposeShieldWindow`**(레벨 19, 화면 전체) + **`Spaces Bar`**(레벨 14, 위쪽 134pt) + `App Icon Window`(레벨 17) 여러 개 | **Spaces Bar 있음** |
| 앱 Exposé (⌃↓) | `ExposeShieldWindow` + `Label Window - <창 제목>`. **`Spaces Bar` 없음** | 아님 |
| 바탕화면 보기 (F11) | `ShowDesktopOverlay`(레벨 18). 쉴드 창 없음 | 아님 |
| 앱 목록 (`Apps`) | 해당 창 없음 (일반 앱 창) | 아님 |

- 실제 화면에서 **Mission Control 위에 노치가 그대로 떠 있었다.** 노치 패널의 창 레벨이 메뉴바 위(`mainMenu + 3`)이기 때문이다. 그래서 직접 숨겨야 한다.
- 창 이름은 비공개 구현이라 macOS 업데이트로 바뀔 수 있다. 그래서 판정 규칙을 한 곳(`MissionControlProbe`)에 모으고, 아래 §2.5의 "신호표 점검"을 릴리스 전 항목에 넣는다.

### 1.2 시점 (열고 닫을 때)

| 순간 | 걸리는 시간 |
|---|---|
| 열기 명령 → 창 서버 이벤트 | 약 +63~83ms |
| 열기 명령 → 쉴드·Spaces Bar 창 나타남 | 약 +90~95ms |
| 닫기 명령 → 창 서버 이벤트 | 약 +52~68ms |
| 닫기 명령 → 쉴드·아이콘 창 사라짐 | 약 +380ms |
| 닫기 명령 → **Spaces Bar 사라짐** | 약 **+520ms** |
| 열고 닫는 애니메이션이 끝날 때 | 이벤트가 한 번 더 (+490~510ms) |

- **이벤트가 창보다 약 20ms 먼저 온다.** 이벤트를 받자마자 한 번만 확인하면 "아직 없음"으로 잘못 판단한다. 이벤트 뒤 약 1.2초 동안 짧은 간격으로 여러 번 확인해야 한다.
- 열자마자 0.35초 뒤 닫는 빠른 토글에서는 열기 명령 뒤 +70ms와 +920ms에, 닫기 명령 뒤 +490ms에 이벤트가 따로 왔다. **이벤트 개수나 순서로 상태를 세면 어긋나므로, 최종 상태는 창 목록으로만 정한다.**

### 1.3 비용

| 작업 | 1회 비용 |
|---|---|
| 창 목록 읽기 (`.optionOnScreenOnly`) | 0.65ms |
| 같은 호출 + 이름 필터 | 0.27ms |
| 창 목록 읽기 (`.excludeDesktopElements` 추가) | 0.17ms |
| 20Hz로 계속 읽기 | 약 1.3% (0.65ms 기준) |

### 1.4 창 서버 이벤트 (비공개)

SkyLight의 `CGSRegisterNotifyProc`로 번호 0~1999을 모두 등록해 어떤 것이 오는지 봤다 (등록된 것은 1488개).

- 오는 것은 **1508, 1325, 1326번** 뿐이었다 (처음 몇 번의 시험에서 1327, 1328이 한 번씩 더 보였지만 반복 시험에서는 나오지 않았다 → 쓰지 않는다).
- 36초 동안 열기·닫기 5쌍과 빠른 토글 3쌍을 했을 때 **총 65건이 모두 명령 뒤 1.2초 안**에 왔고, 관계없는 이벤트는 **0건**이었다. 평소에는 오지 않는다.
- **열림과 닫힘을 구별하지 못한다** (같은 번호가 양쪽에 온다). 그래서 "다시 확인하라"는 깨우는 신호로만 쓴다.
- 이 번호는 macOS 27.3에서 잰 값이고 비공개다. **다른 버전에서는 오지 않을 수 있다.** 이 앱은 이미 SkyLight를 `dlsym`으로 쓰고 있어(잠금화면 창) 같은 방식으로 불러오고, 실패하면 조용히 안전 점검만 쓴다.
- 이벤트를 받으려면 앱의 실행 루프(`NSApplication.run`)가 돌고 있어야 한다. 일반 명령줄 도구에서는 0건이었다.

### 1.5 확인하지 못한 것

- **다중 디스플레이에서의 Mission Control** (창이 디스플레이마다 따로 생기는지, 모든 디스플레이에 동시에 뜨는지)
- Stage Manager, 전체 화면 앱의 Space 안에서 연 Mission Control
- 트랙패드 제스처와 핫코너로 연 Mission Control (키보드·`open`으로만 확인. 같은 창이 뜨므로 같을 것으로 보이지만 미확인)
- 다중 디스플레이에서의 모든 동작 (미러링, 잠금화면, 절전 복귀 포함)

## 2. Mission Control에서 노치 숨기기

### 2.1 구성 요소

| 구성 | 역할 |
|---|---|
| `MissionControlProbe` | 창 목록을 보고 "지금 Mission Control인가"를 정한다. 판정 규칙은 여기에만 둔다 |
| `PanelVisibility`(중재자) | 노치 창의 보임 여부를 **여러 이유의 합**으로 정한다 (§2.4의 7번) |
| `NotchViewModel.hiddenAmount` | 0(보임) ~ 1(숨김). 노치 도형의 폭을 줄이는 값 |

### 2.2 감지 방식

```
깨우기: 창 서버 이벤트(1508·1325·1326) 수신  또는  안전 점검 타이머  또는  앱 활성화·화면 구성 변경·절전 복귀
   ↓
확인(settle): 깨운 뒤 약 1.2초 동안 100ms 간격으로 창 목록을 읽는다 (최대 약 12회 × 0.3ms)
   ↓
판정: WindowManager의 "Spaces Bar" 창이 있으면 Mission Control
   ↓
보이는 중: 100ms 간격으로 확인(Mission Control 중에만), 사라진 것이 연속 2회(약 200ms) 확인되면 끝난 것으로 본다
```

| 항목 | 값 | 이유 |
|---|---|---|
| 평소 | 폴링 없음, 이벤트만 | 대기 CPU·깨어남을 늘리지 않는다 |
| 안전 점검 | 3초마다 (허용 오차 1.5초) | 이벤트가 안 와도 최대 3초 안에 바로잡는다. 0.27ms/3초 = 무시할 수준 |
| 이벤트 불신 | 안전 점검이 이벤트 없이 Mission Control을 먼저 발견하면 "이벤트 경로 불신"으로 표시하고 500ms 폴링으로 전환 | 다른 macOS 버전 대비. 이때 약 0.05% 정도 늘어난다 |
| 시작할 때 | 한 번 확인 | 앱이 Mission Control 중에 켜졌을 때 대비 |

### 2.3 숨김·복귀 동작

**숨김 (Mission Control 시작)**

1. 열려 있는 노치는 먼저 접는다 (눌림·호버·키 입력 포커스 정리). 입력 중이던 글(채팅·메모)은 그대로 보존된다.
2. 노치 도형의 **양쪽 폭이 줄어든다**: 물리 노치가 있는 화면은 노치 폭까지, 없는 화면은 가운데 점까지. 동시에 내용이 투명해진다 (약 0.2초).
3. 끝나면 창의 알파를 0으로 하고 마우스를 통과시킨다 (`ignoresMouseEvents = true`). **창을 내리지(`orderOut`) 않는다.** 내리면 Space 전환 때 깜빡이고, 다시 올릴 때 위치와 순서가 틀어질 수 있다.

**복귀 (Mission Control 끝)**

1. Spaces Bar가 사라진 것이 2회 연속(약 200ms) 확인되면 알파를 1로 올리고 폭이 원래대로 늘어난다 (약 0.28초).
2. 그 뒤에 마우스 처리를 다시 켠다 (`updateHover`가 현재 커서 위치를 다시 판단).

**규칙**

- 숨김 중 새 알림이 오면 **알림 표시 시간 타이머를 멈춰 두었다가** 복귀 뒤에 보인다 (통화 알림 등을 놓치지 않게).
- "동작 줄이기" 설정이 켜져 있으면 폭 줄이기 없이 0.1초 페이드만 쓴다.
- 숨김→복귀→숨김이 0.4초 안에 반복되면 숨긴 채로 둔다 (깜빡임 방지).

### 2.4 일어날 수 있는 충돌·오류와 해결

| # | 문제 | 해결 |
|---|---|---|
| 1 | **앱 Exposé·바탕화면 보기에서 숨겨짐** (Mission Control이 아닌데 숨김) | 쉴드 창이 아니라 **`Spaces Bar`**로 판정. 위 두 가지는 이 규칙에서 제외되는 것을 확인했다 |
| 2 | **이벤트가 창보다 먼저 와서 놓침** | 이벤트 뒤 1.2초 동안 100ms 간격으로 확인 (§1.2) |
| 3 | **빠르게 열었다 닫음** | 이벤트 수가 아니라 창 목록의 최종 상태로 정한다. 복귀는 2회 연속 확인 뒤 |
| 4 | **이벤트가 오지 않음** (macOS 업데이트로 번호가 바뀜) | 3초 안전 점검이 바로잡고, 이벤트 불신이 되면 500ms 폴링 |
| 5 | **숨은 채로 남음** (Mission Control이 아닌데 숨김) | 숨겨진 동안 100ms 확인이 계속 돈다. 앱 활성화·화면 구성 변경·절전 복귀·Space 전환 때도 강제로 다시 확인. 어떤 경우에도 확인 없이 숨김이 유지되지 않는다 |
| 6 | **Mission Control인데 안 숨겨짐** | 이벤트 약 70ms + 확인으로 평균 0.1초 안에 숨김 시작. 놓쳐도 3초 안에 안전 점검이 잡는다 |
| 7 | **잠금 화면 전환과 알파 다툼** — 지금도 `setMainPanelHidden`이 알파를 0/1로 정한다 | 알파를 직접 만지지 않고 **중재자**가 `보임 = !잠금중 && !MissionControl숨김`으로 한 곳에서 정한다 |
| 8 | **숨긴 노치가 클릭을 가로챔** (Mission Control의 창 미리보기가 위쪽에 있다) | 숨기는 동안 `ignoresMouseEvents = true`, 호버·길게 누름·파일 드래그 감시는 중단 |
| 9 | **노치가 펼쳐진 채 Mission Control** | 접기를 먼저 끝낸 뒤 숨긴다. 타이머 숫자 입력 중이면 키 포커스를 돌려준다 (`releaseKeyFocus`) |
| 10 | **애니메이션 도중 상태가 또 바뀜** | 스프링 애니메이션은 중단 가능하고, 목표값(`hiddenAmount`)만 바꾼다 |
| 11 | **다중 디스플레이** | Mission Control은 디스플레이마다 창이 생길 것으로 보이지만 **미확인**. 안전하게 "어느 디스플레이든 Spaces Bar가 있으면 **모든 노치를 함께** 숨기고, 모두 없어지면 함께 복귀" |
| 12 | **Mission Control 중 디스플레이 연결·해제** | 새 패널은 숨긴 상태로 만들고, 복귀 때 함께 보인다 |
| 13 | **메모리 자동 최적화 재시작이 숨김 중에 일어남** | 재시작 직후 시작 확인(§2.2)이 숨김을 다시 판단한다. 재시작은 노치가 닫혀 있을 때만 하므로 Mission Control 중에는 거의 일어나지 않는다 |
| 14 | **창 이름이 OS 업데이트로 바뀜** | 판정 규칙을 한 곳에 모으고, 릴리스 전 신호표 점검(§2.5) |

### 2.5 시험 항목

| 시험 | 합격 기준 |
|---|---|
| ⌃↑, `open`, 트랙패드 제스처, 핫코너로 열고 닫기 20회 | 열릴 때마다 0.3초 안에 숨김 시작, 닫힐 때마다 복귀, 어긋남 0회 |
| 앱 Exposé, 바탕화면 보기, Stage Manager, 런치패드·앱 목록 | 숨지 않는다 |
| 열자마자 닫기(0.2~0.5초 간격) 20회 | 최종 상태가 실제와 같다 |
| 노치를 펼친 채 / 타이머 입력 중 / 채팅 글 쓰는 중 열기 | 접힌 뒤 숨고, 글은 보존, 복귀 뒤 정상 |
| 잠금·잠금 해제 직후 Mission Control | 알파가 어긋나지 않는다 |
| 알림이 숨김 중에 도착 | 복귀 뒤 보인다 |
| 이벤트 등록을 일부러 끈 빌드 | 3초 안전 점검으로 동작, 폴링 전환 |
| 자원: 평소 대기 CPU·깨어남·메모리 | 지금과 같다 (0.12~0.2%, 깨어남 초당 0~2) |
| **신호표 점검** (릴리스 전, 새 macOS마다) | §1.1의 표를 같은 방법으로 다시 기록해 규칙과 맞는지 확인 |

## 3. 다중 디스플레이

### 3.1 요구 정리와 용어

| 요구 | 정리 |
|---|---|
| 노치를 보일 디스플레이 | 연결된 디스플레이 중 **하나** 또는 **모든 디스플레이** |
| 상호작용 | 길게 눌러 연 확장 화면은 **누른 디스플레이에만** 뜬다 |
| 상호작용의 결과 | 미디어 곡 변경, 트레이 파일, 상시 표시 숨김 등은 **모든 디스플레이에 적용** |
| 디스플레이별 상시 표시 | 설정 → 상호작용 → 기본에서 연결된 디스플레이마다 고른다 (§3.4) |
| 대체 옵션 | 선택한 상시 표시가 비활성일 때 주 디스플레이의 상시 표시를 보일지 (§3.4) |

**용어**: **주 디스플레이** = 메뉴바가 있는 디스플레이(`NSScreen.screens.first`, 지금 코드의 `.main`). `NSScreen.main`은 키 창이 있는 디스플레이라 다르므로 **쓰지 않는다.**

### 3.2 구조 — 공유 모델 1개 + 디스플레이별 화면 상태 N개

지금은 `NotchController`(패널 1개) + `NotchViewModel`(화면 상태) + `ActivityCenter`(공유 상태)가 하나씩 있고, 화면 상태와 공유 상태가 `NotchViewModel`에 섞여 있다.

**공유 (이미 하나, 그대로 둔다)**: `ActivityCenter`(일회성 알림, 상시 표시 목록, 상시 표시 숨김 `persistentHidden`), 미디어·트레이·메모·채팅·타이머·일정·AI 사용량 저장소, 설정.

**디스플레이마다 따로 (새로 N개)**: 패널, 호스팅 뷰, `DisplayNotchState`(= 지금 `NotchViewModel`에서 화면 상태만): 노치 크기·물리 노치 여부, 확장 여부, 확장 페이지, 호버, 눌림, 스와이프, 파일 끌기, 채팅 크기.

```
NotchHub (1개)
 ├─ shared:  ActivityCenter, 저장소들, SharedNotchState(마지막으로 본 홈 페이지 등)
 ├─ displays: [DisplayKey: DisplayNotch]      // DisplayNotch = 패널 + 호스팅 뷰 + DisplayNotchState + 컨트롤러
 ├─ expanded: DisplayKey?                      // 확장된 디스플레이는 최대 1개
 └─ visibility: PanelVisibility                // 잠금·Mission Control·"노치 없음"의 합
```

**변경 범위** (현재 코드 기준): `NotchViewModel`을 쓰는 곳은 `NotchController`(44곳), `NotchRootView`(47곳), `AppDelegate`(37곳), `HomeView`(14곳), `TrayStore`(6곳), `LockScreenManager`·`CameraAndCalendar`(각 2곳), `TimerController`(흔들기 1곳)다. `displayTarget`은 `NotchGeometry`, `NotchController`, `LockScreenManager`, 설정 화면에서 쓴다. 대부분 이름 바꾸기 수준의 기계적 변경이고, 동작을 새로 정해야 하는 곳은 §3.5에 모았다.

**상시 표시 투영**: `vm.center.displayed`(`lockActivity ?? transient ?? topPersistent`) 등을 디스플레이별로 거르는 `ActivityFeed`를 둔다. `DisplayNotchState`가 `center` 대신 `feed`를 읽게 하면 나머지 화면 코드는 바뀌지 않는다 (§3.6).

### 3.3 디스플레이 식별과 설정 저장

| 항목 | 방법 |
|---|---|
| 식별 | `CGDisplayCreateUUIDFromDisplayID`의 UUID (이 Mac의 내장 디스플레이에서 값을 얻는 것은 확인). 연결을 껐다 켜도 같은 모니터는 같은 UUID이므로 설정이 유지된다 (다른 모니터에서의 동작은 **미확인**) |
| 표시 이름 | `NSScreen.localizedName` (이 Mac에서 `Built-in Retina Display` 확인). 같은 이름이 둘이면 "모니터 (2)"로 구분하고 화면 배치의 위치(왼쪽/오른쪽)를 함께 보인다 |
| 미러링 | 같은 화면을 복제하는 디스플레이는 **하나로 취급**한다 (`CGDisplayIsInMirrorSet`). 이 처리는 **미확인** |
| 연결 해제 | 설정은 지우지 않고 보관한다. 선택된 디스플레이가 없으면 예전 규칙(노치 있는 화면 → 주 디스플레이)으로 대신 보이고, 다시 연결되면 원래대로 돌아온다 |
| 저장 | `notchDisplays`(`one:<UUID>` 또는 `all`), `displayContent`(UUID → 선택 사전), `displayFallbackToMain`. 이 앱의 설정 규칙대로 `AppSettings`의 **`init`과 `reload()` 두 곳 모두**에서 읽는다 |
| 이전 | 예전 `displayTarget`(`builtIn`/`main`)은 처음 한 번 현재 화면의 UUID로 옮기고, 못 옮기면 예전 규칙을 그대로 쓴다 |

### 3.4 설정 화면

**설정 → 일반 → 표시 화면** (지금의 `내장 / 주` 선택을 바꾼다)

- 목록: 연결된 디스플레이 전체 (이름, 해상도, "주 디스플레이" "내장" 표시) + **모든 디스플레이**.
- 연결 상태가 바뀌면 목록이 바로 갱신된다 (설정 창은 별도 프로세스이므로 거기서도 `didChangeScreenParameters`를 받는다).
- 연결된 디스플레이가 1개면 선택은 비활성화하고 "연결된 디스플레이가 1개입니다"를 작게 보인다.

**설정 → 상호작용 → 기본 → "디스플레이별 상시 표시"** (모든 디스플레이를 고르고 디스플레이가 2개 이상 연결된 때만 보인다)

| 디스플레이 | 선택 |
|---|---|
| (연결된 디스플레이마다 한 줄. 이름, 주 디스플레이 표시) | **모든 상시 표시 컨텐츠** / 개별 상시 표시 항목 (§6의 1번) / **노치만** / **노치 없음** / **주 디스플레이의 설정을 따름** (주 디스플레이 줄에는 이 항목이 없다) |

- 기본값: 주 디스플레이는 "모든 상시 표시 컨텐츠", 나머지는 "주 디스플레이의 설정을 따름".
- 의미: **노치만** = 상시 표시 없이 기본 노치(알림, 길게 눌러 여는 홈)만. **노치 없음** = 그 디스플레이에는 노치를 띄우지 않는다 (알림도 없음).

그 아래 옵션:

> ☐ 선택한 상시 표시가 비활성화인 경우 주 디스플레이의 상시 표시 컨텐츠를 표시
> <small>이 옵션을 끄면 선택한 상시 표시가 비활성화인 경우 기본 노치만 뜹니다.</small>

(문구는 요청하신 그대로 쓴다. 기본값은 켬. 해석은 §6의 1번)

### 3.5 작동 규칙

| 상황 | 규칙 |
|---|---|
| **확장은 한 번에 1개** | 다른 디스플레이에서 길게 누르면, 먼저 열려 있던 디스플레이를 접고(애니메이션 없이 정리) 새 디스플레이를 연다. 타이머 입력·메모 편집·채팅 입력·카메라·파일 트레이 끌기가 모두 하나뿐인 객체라 동시에 열면 충돌한다 |
| **어느 디스플레이에서 열었나** | 길게 누른 디스플레이에만 확장 화면이 뜬다. 바깥 클릭으로 접는 판단도 그 디스플레이의 영역만 본다 |
| **마지막으로 본 홈 페이지** | 접을 때와 페이지를 넘길 때 `SharedNotchState`에 쓰고, 다음에 어느 디스플레이에서 열든 거기서 시작한다 (§6의 3번) |
| **일회성 알림** (볼륨 HUD, 배터리, 통화, 스크린샷 등) | "노치 없음"이 아닌 **모든 디스플레이에 같이** 뜬다. 상세 카드를 눌러 처리하거나 위로 밀어 닫으면 모두에서 닫힌다 (§6의 2번) |
| **상시 표시 숨김** (두 손가락 위로) | `ActivityCenter.persistentHidden`이 공유 상태이므로 모든 디스플레이에 함께 적용된다. 아래로 하면 함께 돌아온다 |
| **호버로 알림 타이머 멈춤** | 지금은 `center.paused`를 컨트롤러 하나가 정한다. 컨트롤러가 여러 개면 한 디스플레이에서 호버 중에 다른 디스플레이가 `false`로 덮어쓴다. **디스플레이별 호버를 모아 "하나라도 호버 중이면 멈춤"**으로 바꾼다 |
| **파일 끌기** | 파일이 들어오는 감지는 디스플레이마다 따로 한다 (각 패널의 위쪽 영역). 끌기 시작 기준(`dragBaseline`)은 모든 컨트롤러가 같은 마우스 누름 이벤트로 갱신한다. 에어드랍·트레이↔AI 채팅 전환 막대도 그 디스플레이 안에서 동작한다 |
| **잠금 화면** | 잠금 노치 창은 지금처럼 1개만 쓴다 (주 디스플레이). 잠겨 있는 동안 **다른 디스플레이의 노치는 모두 숨긴다.** 다중 디스플레이의 잠금화면 동작은 **미확인**이라 1차는 주 디스플레이에만 둔다 |
| **Mission Control** | §2.4의 11번: 어느 디스플레이든 감지되면 모두 숨기고 모두 함께 복귀 |
| **통화·잠금처럼 놓치면 안 되는 항목** | "노치 없음"이 아니면 선택(§3.4)과 관계없이 모든 디스플레이에 표시한다 (§6의 6번) |
| **디스플레이 연결·해제** | `didChangeScreenParameters`는 한 번의 변화에 여러 번 온다. **약 0.6초 모아서 한 번만** 처리한다 (§3.7 3번) |

### 3.6 디스플레이별 상시 표시 결정 규칙

```
persistent(for display d) -> [NotchActivity]?        // nil = 노치 없음
  choice = settings.content[d]                        // 기본값: 주 디스플레이 = all, 그 밖 = followMain
  if choice == followMain, d != main:  d, choice = main, settings.content[main]   // 한 번만 따라간다 (주 디스플레이가 followMain이면 all로 본다)
  switch choice:
    none:      return nil
    notchOnly: return []
    all:       return center.orderedPersistent
    kind(k):   if let a = center.persistent[k] { return [a] }
               // 선택한 항목이 지금 활성이 아님 → '비활성화'
               if settings.fallbackToMain { return persistent(for: main) }   // 재귀 아님: 주 디스플레이의 선택으로 한 번만
               return []                                                     // 기본 노치만
displayed(for d) = center.lockActivity ?? center.transient(d가 none이 아니면) ?? persistent(for: d)?.first
```

- 무한 반복이 생기지 않는다: `followMain`은 한 번만 따라가고, 대체도 한 번만 한다.
- 주 디스플레이가 `none`이고 다른 디스플레이가 `followMain`이면 그 디스플레이도 노치가 없다.
- 이 규칙은 순수 함수이므로 §5의 단위 시험으로 모든 조합(선택 5종 × 대체 켬/끔 × 활성/비활성 × 주 디스플레이 선택 종류)을 숫자로 확인한다.

### 3.7 일어날 수 있는 충돌·오류와 해결

| # | 문제 | 해결 |
|---|---|---|
| 1 | **두 디스플레이에서 동시에 확장** (타이머 입력·메모·채팅·카메라 충돌) | `NotchHub.expanded`로 1개만 허용. 다른 곳을 열면 먼저 접는다 |
| 2 | **알림 타이머가 호버 때문에 멈췄다 풀렸다 함** | 호버를 디스플레이별로 모아 합친다 (§3.5) |
| 3 | **연결·해제 때 패널이 여러 번 만들어졌다 사라져 깜빡임** | 0.6초 모아서 한 번 처리, UUID로 **차이만** 반영 (새로 생긴 것만 만들고, 없어진 것만 내리고, 나머지는 위치만 조정). 패널을 통째로 다시 만들지 않는다 |
| 4 | **선택한 디스플레이가 연결 해제** | 설정은 그대로 두고 예전 규칙(노치 있는 화면 → 주 디스플레이)으로 대신 표시. 다시 연결되면 복귀 |
| 5 | **덮개를 닫아(클램셸) 내장 디스플레이가 없어짐** | 4번과 같음. 노치가 없는 외부 디스플레이는 이미 있는 **가상 노치**(메뉴바 높이, 폭 190pt)로 그린다 |
| 6 | **같은 이름의 모니터 두 대** | UUID로 구분, 목록에는 번호와 화면 배치 위치를 함께 보인다 |
| 7 | **미러링** | 하나로 취급 (§3.3). **미확인**이므로 구현 때 확인한다 |
| 8 | **디스플레이 해상도·배열 변경, 메뉴바 높이 변화** | 변경 때마다 노치 사각형을 다시 계산 (지금도 `reposition`이 함) |
| 9 | **디스플레이 절전 중 그리기** | 절전 중인 디스플레이(`CGDisplayIsAsleep`)는 그리지 않고, 깨어날 때 다시 배치 |
| 10 | **잠금 화면과 패널 보임 다툼** | `PanelVisibility`가 잠금·Mission Control·"노치 없음"을 합쳐 한 곳에서 정한다 (§2.4의 7번) |
| 11 | **상시 표시 선택이 서로 순환** (A가 B를, B가 A를 따름) | `followMain`은 주 디스플레이만 가리킨다 (§3.6). 주 디스플레이는 따를 수 없다 |
| 12 | **채팅이 두 화면에 동시에 활성** (`ChatStore.visible`이 하나뿐) | 확장은 1개이므로 채팅 페이지도 1개. 확장이 안 된 디스플레이에는 페이지 뷰 자체가 만들어지지 않는다 |
| 13 | **파일 끌기 감지가 두 번 동작** | 각 컨트롤러가 자기 패널의 위쪽 영역에서만 판단하고, 확장된 쪽만 끌기 상태가 된다 |
| 14 | **설정 창(별도 프로세스)이 모르는 디스플레이** | 설정 창에서도 `NSScreen`으로 같은 UUID를 만든다. 설정 값은 기존 분산 알림(`settingsChanged`) 경로로 본 앱에 전달한다 |
| 15 | **개발용 명령·시험 도구가 첫 번째 디스플레이만 봄** (`notchctl`) | `display:<UUID 또는 번호>` 대상 지정을 추가한다 |
| 16 | **디스플레이마다 패널·뷰가 생겨 메모리·CPU 증가** | §3.8의 예산. "노치 없음"인 디스플레이에는 패널을 만들지 않는다 |
| 17 | **전체 화면 앱, Space 전환** | 패널의 `canJoinAllSpaces`·`fullScreenAuxiliary`는 지금과 같다. 다중 디스플레이의 전체 화면 동작은 **미확인** |

### 3.8 자원 예산

| 항목 | 기준 |
|---|---|
| 디스플레이 1개 | 지금과 같다 (메모리 약 18MB, 대기 CPU 0.12~0.2%, 깨어남 초당 0~2) |
| 디스플레이 추가 1개 | 메모리 **+6MB 이하**, 대기 CPU **+0.05% 이하**, 새 타이머·폴링 없음 |
| "노치 없음"인 디스플레이 | 패널·호스팅 뷰를 만들지 않는다 (추가 비용 0) |
| 디스플레이 연결·해제 20회 반복 | 누수 0건, 메모리가 연결 횟수에 비례해 늘지 않는다 (패널은 내릴 때 `contentView = nil`로 내용을 떼어 낸다 — 잠금 노치 창이 이미 쓰는 방식) |
| Mission Control 감지 | §2.5의 자원 기준 |

## 5. 시험 계획

이 Mac에는 디스플레이가 1대뿐이라 다음 네 가지를 함께 쓴다.

| 방법 | 용도 | 상태 |
|---|---|---|
| **단위 시험** (`--display-probe`, 개발 빌드): 가짜 디스플레이 목록과 설정을 주고 §3.6의 결과를 출력 | 상시 표시 결정의 모든 조합, 이전(마이그레이션), UUID 처리 | 만들 수 있음 |
| **가짜 두 번째 패널** (`DMN_FAKE_DISPLAYS=2`, 개발 빌드): 같은 화면에 디스플레이 하나를 더 흉내 내어 패널 2개를 만든다 | 확장 1개 규칙, 호버 합치기, 알림 공유, 메모리·CPU 증가량(§3.8) | 만들 수 있음 |
| **가상 디스플레이** (`CGVirtualDisplay`, 비공개 API): 진짜 두 번째 `NSScreen`을 만든다 | 연결·해제, 배열 변경, 선택한 디스플레이 이동 | 클래스 4개가 이 Mac에 있는 것은 확인. **실제로 만들어 보지는 않았다** (화면 구성이 잠깐 바뀌므로 구현할 때 해 본다) |
| **실제 외부 모니터** | 가상 노치(노치 없는 화면), 미러링, 잠금화면, 전체 화면 앱, 덮개 닫기, 절전 복귀, Mission Control | 사용자가 확인 (§6의 7번) |

## 6. 결정이 필요한 것

1. **"선택한 상시 표시가 비활성화인 경우"를 어떻게 읽을지.** 이 문서는 아래처럼 읽었다.
   - 디스플레이마다 **개별 상시 표시 항목**(예: "미디어", "AI 사용량")도 고를 수 있고, 그 항목이 지금 **활성이 아닐 때**(재생 중이 아님 등)를 "비활성화"로 본다. 이때 옵션이 켜져 있으면 주 디스플레이가 보이는 상시 표시를 대신 보이고, 꺼져 있으면 기본 노치만 보인다.
   - 이렇게 읽은 이유: 목록이 "모든 상시 표시 / 노치만 / 노치 없음 / 주 디스플레이 따름" 네 가지뿐이면 모든 디스플레이가 같은 상시 표시 풀을 공유하므로 "비활성화"가 생길 수 없고, 이 옵션이 아무 일도 하지 않게 된다.
   - **다르게 의도하셨다면 알려 주세요.** 네 가지만 쓰시려면 개별 항목 선택을 빼고 이 옵션의 의미를 다시 정해야 한다.
2. **일회성 알림(볼륨 HUD 등)**을 모든 디스플레이에 같이 띄울지, 주 디스플레이에만 띄울지. (제안: 모든 디스플레이, "노치 없음"은 제외)
3. **마지막으로 본 홈 페이지**를 디스플레이끼리 공유할지, 디스플레이마다 기억할지. (제안: 공유. 요청하신 트레이 예시와 같은 흐름)
4. **"모든 디스플레이"를 처음 켤 때의 기본값.** (제안: 주 디스플레이 = 모든 상시 표시, 나머지 = 주 디스플레이 따름)
5. **대체 옵션의 기본값.** (제안: 켬)
6. **통화·잠금** 같은 놓치면 안 되는 항목은 선택과 관계없이 "노치 없음"이 아닌 모든 디스플레이에 표시할지. (제안: 표시)
7. **시험 환경.** 외부 모니터가 있는지, 있다면 구현 중간에 실제 확인을 부탁드려도 되는지. 없다면 가상 디스플레이로 가능한 범위까지 하고, 나머지(가상 노치, 미러링, 잠금화면, 전체 화면, 덮개 닫기)는 미확인 항목으로 릴리스 노트에 적겠다.
